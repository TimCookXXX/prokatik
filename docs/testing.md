# Тесты и проверки

## Чем проверяется код

| Команда | Что делает | Состояние |
|---|---|---|
| `pnpm test` | Vitest, один прогон | работает |
| `pnpm test:watch` | Vitest в watch-режиме | работает |
| `pnpm exec next typegen` | генерирует типы роутов, не собирая проект | работает |
| `pnpm exec tsc --noEmit` | проверка типов по всему проекту | нужен свежий `typegen`, см. ниже |
| `pnpm check-theme` | проверяет, что в `theme/tokens.css` есть все обязательные токены | работает |
| `pnpm check-storage` | круговая проверка S3: запись, чтение, публичная ссылка, удаление | требует заполненных `STORAGE_*` |
| `pnpm seo:check <url>` | техническое SEO живого сайта: коды ответа, порядок контента, canonical, noindex, robots.txt, OG, JSON-LD, sitemap | требует запущенного сайта; см. ниже |

Перед коммитом осмысленный минимум — `pnpm test` и проверка типов.
Если трогали `theme/tokens.css` — ещё и `pnpm check-theme`.

## Проверка типов зависит от типов роутов

При `typedRoutes: true` типы ссылок и параметров генерирует сам Next, и `tsc`
их только читает. Что именно он прочитает, зависит от того, что запускалось до
него: `next build` и `next dev` пишут типы в разные каталоги. Поэтому проверять
типы надёжнее так:

```bash
pnpm exec next typegen && pnpm exec tsc --noEmit
```

Команда `typegen` для того и существует — она даёт типы роутов без полной
сборки. Если `tsc` выдаёт `TS2307` на роут, который точно есть, — типы
устарели, помогает `rm -rf .next` перед `typegen`.

## Линтера в проекте нет

Конфигурации ESLint в репозитории не существует: ни `.eslintrc*`, ни
`eslint.config.*`. Скрипта `lint` в `package.json` тоже нет — в Next 16 команда
`next lint` удалена, её заменяет прямой вызов ESLint CLI. Роль статической
проверки выполняет `tsc --noEmit` со `strict: true`.

Сам пакет `eslint` в `devDependencies` оставлен намеренно — как заготовка под
flat-config; `eslint-config-next` убран вместе со скриптом, он был привязан к
удалённой команде.

`NEEDS REVIEW`: заводить ли ESLint через flat-config. По коду нельзя понять,
был линтер потерян при миграции или от него отказались сознательно.

## Устройство тестов

- Runner — **Vitest**, окружение `jsdom`, конфиг `vitest.config.ts`.
- Тесты лежат **только в `tests/**`** и подхватываются по маске
  `tests/**/*.test.ts(x)`. Файлы рядом с исходниками не собираются — если
  положить тест в `src/`, он просто не запустится.
- Структура `tests/` зеркалит `src/`.
- Импорты внутри тестов — через те же псевдонимы, что и в коде: `@/`, `@theme/`,
  `@db/`. Они продублированы в `vitest.config.ts`.
- Общий setup — `tests/setup.ts`, там подключается `@testing-library/jest-dom`.
- JSX задан явно (`esbuild: { jsx: "automatic" }`): Vitest идёт через esbuild и
  `tsconfig.json` в этой части не читает. Значение продублировано намеренно —
  так тесты не зависят от того, что впишет в `tsconfig` `next typegen`.

## Что покрыто

Живого Postgres тесты **не требуют** — это принципиальное свойство набора.

| Область | Как тестируется |
|---|---|
| Доменная логика | чистые функции: занятость, статусная машина, даты, фильтры, слаги, разбор пути объявления |
| Права в переписке | `src/lib/chat/rules.ts` — чистые функции над уже прочитанными строками: кто кому может писать, кто что видит. В базу модуль не ходит именно ради этого |
| Сборка ленты чата | `src/lib/chat/grouping.ts` — группировка сообщений, разделители дат и непрочитанного, поиск и фильтры списка. Проверяется в том числе независимость от порядка прихода сообщений: в задаче о вебсокетах массив начнёт доливать сокет |
| Сценарии входа | `src/lib/auth/flows.ts` через порт `store.ts` — фейковая реализация в памяти (`tests/fixtures/auth-store.ts`) вместо базы |
| Токены, пароли, стоп-лист | напрямую |
| Гарда доступа | `middleware()` на собранных вручную `NextRequest`: редирект анонима с защищённых префиксов, сохранение пути и query в `?from=`, обе формы session-cookie, границы префиксов и сам матчер |
| Доступ к сокету | `src/lib/realtime/access.ts` — вердикт по уже прочитанной строке сессии (срок, бан) и allow-list `Origin`, включая отказ при отсутствующем `Origin`. Процесс `realtime` живёт вне Next, ни middleware, ни гарды страниц его не прикрывают, и это единственное покрытие его поверхности |
| Контракт события доставки | `src/lib/realtime/events.ts` — сборка payload (получатели строятся только из участников треда) и разбор: битый JSON и неизвестный вид дают `null`, а не исключение. Исключение в обработчике `notification` уронило бы процесс, а `restart: unless-stopped` перезапустил бы его в цикл |
| Стор реального времени | экземплярность (два стора не делят состояние — иначе счётчик одного человека утёк бы другому на SSR) и правило «стор ?? проп»: при потере связи бейдж возвращается к серверному числу |
| Схема БД | shape-тесты: проверяется наличие таблиц и колонок в `drizzle/schema.ts`, без подключения. Плюс сверка `notificationKind.enumValues` со списком в `src/lib/notifications/kinds.ts`: слой db не импортирует из lib, и разъехаться им не даёт только этот тест |
| Переменные окружения | `parseEnv` на наборах значений, включая production-ветку |
| Компоненты | Testing Library: рендер и поведение (шапка, поиск, формы, галерея, фильтры) |
| Загрузка файлов | route-хендлер с замоканными S3 и sharp; есть фикстуры-картинки в `tests/fixtures/images/` |
| SEO | JSON-LD, robots, sitemap, метаданные и пустые страницы каталога (404, `noindex`), отсутствие `loading.tsx` в каталоге, разбор ответов для `seo:check` |

Именно ради тестируемости без базы auth-логика вынесена в чистые функции с
инъекцией зависимостей: Server Actions — тонкие обёртки, которые собирают
`store`, `sendMail` и лимиты, а вся логика лежит в `flows.ts`.

**Количество тестов здесь намеренно не указано** — оно меняется с каждой
задачей. Текущее значение выводит `pnpm test`.

## Как писать новый тест

1. Файл кладётся в `tests/`, путь повторяет расположение в `src/`.
2. Имя — `*.test.ts` или `*.test.tsx`.
3. Логику тестируем как чистую функцию. Если для этого нужна база — скорее
   всего, логику стоит вынести из Server Action в `src/lib/**`, как сделано с
   auth.
4. Внешние сервисы (S3, SMTP, fetch) мокаются. Для почты есть
   `__setTransportForTests`, для S3 — `_resetR2ClientForTests`.

## Локальное S3 (MinIO)

Загрузка картинок и бэкапы завязаны на S3-совместимое хранилище, которого в
обычном локальном окружении нет — поэтому по умолчанию `/api/upload` отвечает
503, а бэкапы не проверить вовсе. Для этого в `docker-compose.yml` есть MinIO
под профилем `dev`:

```bash
pnpm dev:up      # база + MinIO с готовыми бакетами
pnpm dev:down    # погасить
```

Профиль `dev` сам не активируется, поэтому на проде `docker compose up -d`
эти сервисы не поднимает — там работают только caddy, app, db и backup.

Поднимается MinIO с двумя бакетами, повторяющими прод: `inrenta-media` с
публичным чтением (фото и обложки) и приватный `inrenta-backups` (дампы).
Веб-консоль — `http://localhost:9001`, логин и пароль `minioadmin`.

Дальше в `.env`:

```bash
STORAGE_ENDPOINT=http://localhost:9000
STORAGE_BUCKET=inrenta-media
STORAGE_ACCESS_KEY_ID=minioadmin
STORAGE_SECRET_ACCESS_KEY=minioadmin
STORAGE_PUBLIC_BASE=http://localhost:9000/inrenta-media

BACKUP_S3_ENDPOINT=http://minio:9000
BACKUP_S3_BUCKET=inrenta-backups
BACKUP_S3_ACCESS_KEY_ID=minioadmin
BACKUP_S3_SECRET_ACCESS_KEY=minioadmin
```

**Эндпоинты у них разные, и это не опечатка.** Приложение запускается на хосте
(`pnpm dev`) и ходит в MinIO через проброшенный порт — `localhost:9000`. Скрипт
бэкапа работает внутри контейнера, где `localhost` это он сам, поэтому ему нужно
имя сервиса — `minio:9000`. MinIO для этого подключён к сети основного стека.

После правки `.env` **перезапустить dev-сервер**: `next.config.ts` собирает
список разрешённых хостов для `next/image` из `STORAGE_PUBLIC_BASE` на старте, и
без перезапуска картинки получат 400 от оптимизатора.

Второе условие для локальных картинок — послабление `dangerouslyAllowLocalIP` в
`next.config.ts`. Next 16 по умолчанию отказывается оптимизировать картинки с
приватных адресов (защита от SSRF), а MinIO живёт на `localhost:9000`.

Послабление работает **только под `pnpm dev`**. Локальная прод-сборка
(`pnpm build && pnpm start`) отдаст на фото 400 от оптимизатора: `next build`
выставляет `NODE_ENV=production` и запекает запрет в сборку. Это не поломка, а
следствие того, что ослаблять прод-сборку ради локального MinIO нельзя.

Проверка загрузки без браузера:

```bash
curl -s -c /tmp/c.txt -o /dev/null -L http://localhost:3000/api/dev/login
curl -s -b /tmp/c.txt -F "image=@tests/fixtures/images/small.jpg" \
  http://localhost:3000/api/upload
```

В ответе — публичный адрес файла; он должен открываться анонимно и отдавать
`image/webp` независимо от исходного формата.

Прогон бэкапа и восстановления — в [RECOVERY.md](RECOVERY.md); запускать
`docker compose up -d backup` и дать контейнеру секунд десять: он ставит
`aws-cli` при старте.

Вернуть окружение к обычному состоянию — очистить обе группы переменных и
выполнить `pnpm dev:down` (с `-v`, если нужно снести и данные MinIO).

## Ручные проверки

Автотесты не видят реальную БД, cookie, редиректы, письма и вёрстку. Для входа
по почте есть отдельный чеклист: [QA-email-auth.md](QA-email-auth.md).

**Доставка в реальном времени** проверяется руками — автотестов на два процесса
нет: два браузера с разными аккаунтами (`/api/dev/login`), сообщение приходит без
перезагрузки и всплывает уведомлением; кружок появляется на аватарке в шапке и в
таб-баре; своя же открытая переписка всплывашки не даёт; две вкладки одного человека; обрыв и восстановление; рестарт
`realtime` при живом `app` и наоборот; поведение при выключенном `realtime`
(лента должна вести себя как до задачи); сокет с телефона по `192.168.x.x`.

Локально процесс поднимается `pnpm dev:realtime` рядом с `pnpm dev`.

Перед деплоем — предполётный список в [DEPLOY.md](DEPLOY.md).

## Проверка SEO живого сайта

`pnpm seo:check <url> [--delay 600] [--sample 15] [--browser-ua]`
(`scripts/seo-check.ts`) ходит по сайту с UA YandexBot — Next отдаёт ему
метаданные в `<head>`, а не стримом в body, то есть видит то же, что робот.
Адреса берёт из sitemap. Печатает таблицу `PASS/FAIL/SKIP/INFO`, при любом
FAIL код выхода 1. Что именно проверяется — комментарии к шагам в самом
скрипте; правила, которые он сторожит, — в [seo.md](seo.md).

Запросы идут строго по одному, на прод — с паузой 600 мс (для localhost — без
паузы), карточек из sitemap — выборка. Локально проверяется
production-сборка (`pnpm build && pnpm start`) — то, что поедет на прод: под
`pnpm dev` коды ответа расходятся с ней (так, `?page` за концом выдачи там
отдаёт 200, а в сборке — 404).

Проверки Open Graph и `priceSpecification` в JSON-LD карточки сейчас дают FAIL:
ни того, ни другого на сайте пока нет.

## Локальные грабли

- **Перед `pnpm build` остановить dev-сервер**: у них общий каталог `.next`.
- **Локальная сборка `realtime` через esbuild может упасть на чужом
  `~/.pnp.cjs`.** esbuild поднимается по дереву каталогов и подхватывает
  манифест Yarn PnP из домашней директории, после чего отказывается резолвить
  `ws` и `zod`. К коду это отношения не имеет; в Docker-сборке проблемы нет,
  контекст там чистый.
- **Типы роутов держатся в двух местах и протухают.** `next build` пишет их в
  `.next/types`, `next dev` — в `.next/dev/types`; оба каталога перечислены в
  `include` из `tsconfig.json`. После удаления роута остаётся мусор и появляются
  ложные `TS2307`. Лечится `rm -rf .next && pnpm exec next typegen`.
- **`next dev` дописывает блок в `CLAUDE.md`** — раздел между маркерами
  `nextjs-agent-rules`. Он создаётся заново при каждом запуске, поэтому удалять
  его из дифа бесполезно: проще коммитить вместе с работой. Генератор —
  `node_modules/next/dist/server/lib/generate-agent-files.js`, выключателя у
  него нет.
- **`next typegen` правит `tsconfig.json` сам** — например, выставляет
  `"jsx": "react-jsx"` и дописывает пути типов. Это ожидаемо; если после его
  запуска в дифе всплыл `tsconfig.json`, изменения надо просмотреть, а не
  откатывать вслепую.
- **После `pnpm build` первый `pnpm dev` может упасть** с `Cannot find the
  middleware module` — сборка оставляет `.next` в состоянии, которого
  dev-сервер не ожидает. Здесь половинчатая чистка не поможет, нужно
  `rm -rf .next` целиком.
