# План: поиск «Что · Когда · Где»

Крупная задача, план живёт здесь до её завершения (CLAUDE.md, «Рабочий процесс»).
Источник переноса — рабочее дерево `sravniprokat/` (далее **SP**; база —
коммит `eea5c60` плюс незакоммиченные правки на 2026-10-03, их и берём).
Пути без префикса — inrenta. Редакция 2 — после независимого ревью (§9).

## 0. Решения пользователя по вопросам плана

План утверждён 2026-10-03, все четыре ответа — рекомендованные варианты:

1. **Выдача через границу города** — (а): когда в адресе есть точка, выдача
   берёт все активные города того же `geo_region` (§2.5). Без точки — один
   город, как сейчас.
2. **Адрес владельца публично** — улица / ЖК / пункт без номера дома;
   расстояние до дома точное, без снапа к сетке (§2.7).
3. **Точка покупателя в URL** — 3 знака (≈ 100 м); для геолокации подпись `la`
   без номера дома; хиты Метрики без `loc/la` — BACKLOG (§2.6).
4. **Календарь «Когда»** — взаимодействие SP на `react-day-picker` в теме
   inrenta, на десктопе поповер под полем (§4).

## 1. Цель и рамки

**Что меняется.** Мёртвый поиск (одна строка, ILIKE, без подсказок) становится
панелью из трёх частей:

- **Что** — умные подсказки по живым объявлениям города и по разделам. Поиск на
  `/search` работает тем же движком и с тем же ранжированием.
- **Когда** — выбор диапазона дат. Выдача фильтруется по занятости, карточка
  показывает свободу на выбранные дни, даты доходят до виджета брони.
- **Где** — адрес или геолокация пользователя. Выводится расстояние до вещи, есть
  сортировка «Ближе». Для этого у объявления появляется обязательный адрес с
  точкой и признаком точности, а геокодер переносится из SP целиком.

**Чего задача осознанно не делает** (кроме OSRM, ушедшего в BACKLOG, это просто
не входит в задачу):

| Не делаем | Почему |
|---|---|
| Модель сравнения SP (группы, классы, бренды, модели, офферы, прокаты, лиды) | Решение пользователя: переносим механику, не модель |
| Маршрут `/{city}/poisk`, `targetHref`, уровни `resolveExact` (модель/бренд/класс/чипы) | Завязаны на модель сравнения. Остаётся `/search?city=` |
| OSRM, дорожные расстояния, таблицы пробок, минуты в пути | Отдельный контейнер на 346 МБ с ежемесячной пересборкой не влезает в 1 ГБ. Минуты по прямой откалиброваны под машину в Краснодаре и для «забрать у соседа» вводят в заблуждение → BACKLOG |
| Карта (тайлы, пин на карте) | Нужны тайлы и правка CSP → BACKLOG |
| Фильтр по радиусу и bbox-индекс | Достаточно сортировки «Ближе». Индекс понадобится вместе с радиусом → BACKLOG |
| Выдача по региону **без** точки «Где» | Без точки нет расстояний, и смешивать города незачем. С точкой — §0 вопрос 1 |
| Перенос конвейера сборки геоданных (`prepare.sh`, `build.py`, ГАР/OSM) и сборка других регионов | Первая порция данных — готовый `index.krasnodar.json` из SP → BACKLOG |
| Справочник микрорайонов и округов SP (`districts`, `matchPlaces`, `okrug-bounds`) | Данные на 36 строк вручную и только для Краснодара; геокодер и так знает микрорайоны как места → BACKLOG |
| `GEOCODER_INDEX_FILE` (загрузка JSON в рантайме) | Таблицы всё равно нужны; для `yablonovskiy` этот путь сломан; разбор 80 МБ — пик памяти (critic B2) |
| `/api/geo/resolve`, `geocodeShopAddress`, `scripts/geocoder-eval` | Переходный или специфичный для SP код |
| Админка синонимов поиска | Синонимы лежат в коде рядом с деревом категорий → BACKLOG |
| Расстояние в подсказках «Что» | Подсказки ранжируются по тексту; расстояние — в выдаче → BACKLOG |

## 2. Решения по открытым вопросам

### 2.1. «Что»: где живёт индекс

**Решение: индекс в памяти процесса `app`, по одному на город, и GET-роут
подсказок с дебаунсом.** Клиентский индекс и SQL отклонены.

- **Клиентский индекс** (как в SP) отклонён. SP отдаёт клиенту курируемый каталог
  на ~12 КБ. Здесь же это пользовательские заголовки, и их число растёт с
  маркетплейсом: 10 тыс. объявлений — это мегабайты JSON на каждую страницу и
  линейный скоринг на телефоне на каждое нажатие.
- **SQL** (`pg_trgm`/tsvector) отклонён. Раскладку, транслит, гомоглифы и
  стемминг SP в SQL пришлось бы переписать, и ранжирование подсказок разошлось бы
  с ранжированием выдачи. Расширений в образе `postgres:16-alpine` тоже нет. Это
  путь на будущее, когда индекс перестанет помещаться в память → BACKLOG.
- **Сервер.** `src/server/search-index.ts` держит `Map<cityId, CityIndex>` на
  `globalThis.__inrentaSearchIndex`. `globalThis` нужен затем, чтобы роут, страница
  и server action видели один кэш даже при раздельных бандлах; это тот же приём,
  что у движков геокодера в SP.
- **Сборка индекса.** Один SQL-запрос по городу: `listings.status = 'active'`,
  `users.banned_at IS NULL`, `cities.is_active`, join категорий. Скрытые,
  архивные и забаненные в индекс не попадают вовсе. Стоп-слова городов берутся
  из живого списка активных городов **в момент сборки**.
- **Инвалидация в два контура.**
  1. Явная `invalidateSearchIndex()` (чистит все города) в `createListing`,
     `updateListing`, `setListingStatus`, `adminSetListingStatus`,
     `adminBanUser`, `adminUnbanUser`, `adminCreateCategory`,
     `adminDeleteCategory`, `adminCreateCity`, `adminUpdateCity`,
     `adminSetCityActive`. Владелец видит свою правку сразу; переименованный
     или новый город сразу становится стоп-словом.
  2. Версия города `count(*), max(updated_at)` по активным строкам, сверка не
     чаще раза в 30 с. Ловит сиды и правки из других процессов.
- **Роут** `GET /api/search/suggest?city=<slug>&q=[&from&to]`. Ответ:
  `{ items: [{id, title, priceDay, href, categoryName, photoUrl|null}] ≤ 6,
  categories: [{name, href, count}] ≤ 4 }`.
  - Пустой или односимвольный `q` возвращает популярные разделы (по счётчикам
    города).
  - **Даты.** Если пришёл валидный диапазон (те же правила, что `parseFilters`,
    §4), верхние 50 кандидатов по score проверяются одним SQL `freeInRange` по
    `inArray(listings.id, ids)`, в ответ идут первые 6 свободных. Так подсказки
    согласованы с выдачей при выбранных датах (решение 4) и не ведут на
    карточку, где виджет сразу скажет «Занято».
  - `href` у объявления и раздела — **канонический** путь
    (`listingPath`, `/{city}/{root}/{sub}`) без query; переносимые параметры
    клиент дописывает сам (§2.6).
  - Заголовок `Cache-Control: private, max-age=30`.
  - Лимит `search` 300/мин на IP (§2.11); сверх лимита — 429 и пустой ответ.
  - Почему роут, а не Server Action: actions — это POST, клиент выполняет их
    очередью и они не кэшируются. Подсказкам нужен параллельный кэшируемый GET.
    Это попадает в исключения из `docs/architecture.md`.
- **Клиент.**
  - Дебаунс 100 мс.
  - LRU-кэш ответов на 50 записей по ключу `city|q|from|to`.
  - Защита порядка `seq`/`shouldApply` из SP: старый ответ не перетирает новый,
    запрос не обрывается.
  - Популярные разделы запрашиваются при фокусе и кэшируются.
  - Подсветка совпавших начал слов считается на клиенте общей чистой функцией
    `highlight` — той же, что у сервера.
- **Состояния списка «Что»** (тексты — в `theme/content.ts`):
  | Состояние | Что видно |
  |---|---|
  | фокус, пусто | «Популярные разделы» |
  | есть подсказки | разделы, объявления, последней строкой — «Показать все по «q»» (ведёт на `/search`, достижима стрелками) |
  | `q` не пуст, подсказок нет | «Точных подсказок нет — нажмите «Найти», поищем «q» во всех объявлениях» и та же строка «Показать все по «q»» |
  | запрос в полёте | прежний список остаётся, без спиннера |
  | 429 / сеть / 5xx | как «подсказок нет»: строка «Показать все по «q»» всегда работает |
- **ARIA** (исправляем два дефекта SP, sp-what.md:147-148): `aria-controls`
  только когда список смонтирован; вежливая live-область «N подсказок»; у
  каждого `role="search"` свой `aria-label` («Поиск по объявлениям» в шапке,
  «Поиск на главной» в hero).
- **Активная строка с клавиатуры.** Комбобокс использует
  `aria-activedescendant`, у опций нет реального фокуса и hover, а `.hoverable`
  красит только наведение мышью. Поэтому в `globals.css` добавляется правило
  `[role="option"][data-active="true"]` с фоном `--color-hover` (у токена
  смысл «наведение и тап» — ближе к курсору, чем охряное `--color-selected`).
  Токен не новый, `tokens.css` не трогаем. Проверяется в `WhatField.test` и
  гардом `tests/theme/states.test.ts`.
- **Масштаб.**
  - **Память.** Запись — это заголовок, слова раздела и до 50 слов описания:
    порядка 1 КБ. 10 тыс. объявлений — порядка 10 МБ (оценка, на этапе 1
    проверяется замером).
  - **Скорость.** Скоринг SP перебирает все записи, и `editDistance` на каждом
    сравнении выделяет матрицу. Поэтому переносим с одной оптимизацией: словарь
    уникальных слов города и постинги. `wordScore(t, w)` считается один раз на
    уникальное слово, затем агрегируется по записям. Семантика не меняется; тест
    сверяет результат с наивным перебором.
  - Бюджет: подсказка p95 < 30 мс на 10 тыс. синтетических объявлений. Меряется
    скриптом в scratchpad, результат вписывается в ADR 0022.

### 2.2. «Что»: модель совпадения для объявлений

Нормализацию, токены, `tokenForms`, `wordScore`, `editDistance`, `stem`,
`switchLayout`, `transliterate`, `fixHomoglyphs`, `subsets` и `highlight`
переносим из `SP:src/lib/compare/search.ts` и `models.ts:5-15` без изменения
поведения. Меняется только состав записей.

**Запись объявления:**

| Поле | Состав | Вес |
|---|---|---|
| `own` | слова заголовка | 1 |
| `context` | имя раздела, имя корня, `keywords` раздела | 0.6 (`CONTEXT_WEIGHT`) |
| `extra` | первые 50 слов описания; только точное совпадение, префикс или стем, без фаззи и подстроки | 0.35 |

**Запись раздела** (подраздел или корень, у которого есть активные позиции в
городе):

- `own` — имя и `keywords`;
- `context` — имя корня;
- бонус 0.2 плюс `min(count, 20) × 0.01`, как `shops` в SP.

**Правила отбора:**

- Каждый токен запроса обязан совпасть (AND).
- В **подсказки** объявление попадает, только если каждый токен совпал в
  `own ∪ context`. Совпадение только по описанию подсказкой не считается.
- На `/search` достаточно совпадения в `own ∪ context ∪ extra`.
- Порядок одинаковый: score по убыванию, затем `createdAt` по убыванию. Поэтому
  при тех же `q`, датах и **без фасетов** (цена, залог, раздел) верх `/search`
  совпадает с подсказками, а совпадения только по описанию уходят в хвост. Это
  проверяется тестом (R8).
- Правило SP «хотя бы один токен в `own`» остаётся только для разделов. Для
  объявлений оно убрало бы «болгарка» → «УШМ Makita» (совпадение по `keywords`
  раздела), а именно такое совпадение здесь и нужно.
- Слишком короткий запрос (`compact(q).length < 2`) считается пустым.

**Синонимы. Решение: в коде, два уровня, без схемы и админки.**

1. `keywords?: string[]` у разделов в `src/lib/seed/categories.ts` — в
   единственном месте, где дерево и так задано кодом. В рантайме берётся по слагу.
   Раздел, заведённый в админке, ключевых слов не имеет, пока их не добавят в код.
2. `src/lib/search/synonyms.ts` — группы равнозначных слов (`болгарка/ушм`,
   `велик/велосипед`, `сап/sup/сапборд` …). Каждая группа даёт токену
   дополнительные формы с весом 0.9.
   - Первичное наполнение — по 61 заголовку `seed_real/listings.csv` и дереву
     категорий.

**Стоп-слова.** Слова SP (`прокат`, `аренда`, `взять`, `цена`, `сутки`,
предлоги) плюс названия активных городов в именительном и предложном падежах из
`cities`. Захардкоженный в SP «краснодар» убирается.

**Подмножества при нуле.** Если весь запрос из двух и более токенов ничего не
нашёл, `/search` пробует подмножества (`subsets` из SP, k = n−1…1) и показывает
плашку «По «…» ничего — показываем по «…»». В подсказках подмножеств нет.

### 2.3. `/search`: релевантность и пагинация в SQL

- `rankListingIds(cityIds, q)` (`src/server/search.ts`) возвращает
  `{ ids: string[] (≤ 1000, по релевантности), usedQuery, dropped }`.
  `cityIds` — один город или города региона (§2.5).
- `searchListings` и `getSearchFacets` вместо `textConditions` получают
  `inArray(listings.id, ids)`. **Не** `= ANY(${ids})`: шаблон `sql` у drizzle
  разворачивает JS-массив в `($1, $2, …)`, а не в массив Postgres.
- Сортировка «Подходящие» —
  `ORDER BY array_position(${sql.param(ids)}::text[], ${listings.id}), listings.id`
  (`listings.id` — `text`, драйвер `pg` передаёт JS-массив как массив
  Postgres). Тест проверяет текст SQL через `.toSQL()` и порядок на моке.
  Остальные сортировки работают как раньше, поверх того же фильтра по id.
- LIMIT/OFFSET и `count(*)` остаются в SQL, вместе с фильтрами, датами и
  фасетами. Потолок в 1000 совпадений фиксируется в ADR 0022 как граница схемы.
- **Сортировка по умолчанию:**
  - `q` есть → `relevance`;
  - `q` нет, а точка «Где» есть → `near`;
  - иначе → `new`.

  Умолчание в адрес не пишется. Явное `sort=new` теперь допустимо, потому что при
  `q` новизна больше не умолчание.
- **Меню сортировки показывает действующую сортировку.** `parseFilters`
  возвращает уже **эффективную** сортировку (с учётом умолчания), и именно она
  уходит в `SortMenu current`, а не сырой `searchParams.sort`. Сейчас меню при
  пустом `sort` подсвечивает первый пункт «свободные», хотя порядок — «новые»;
  это чинится попутно. Список опций по контексту (`relevance` только при `q`,
  `near` только при точке и регионе) строится там же — `sortOptionsFor(filters)`
  в `filters.ts`.
- **Аварийный путь.** Если сборка индекса упала, `textConditions` (ILIKE)
  остаётся как деградация с `console.error`. Другой роли у ILIKE больше нет.

### 2.4. Где стоит панель

Одна форма `role="search"` на поверхность (в шапке — одна, без дубля
«десктоп + телефон» в DOM): раскладка меняется классами.

| Поверхность | Вид |
|---|---|
| Шапка, ≥ `lg` | Инлайн-панель в 48 px: `[Что, flex-1] │ [Когда] │ [Где] [🔍]`. Списки «Что» и «Где» и календарь (два месяца) — поповеры через портал (§ ниже) |
| Шапка, < `lg` (телефон и планшет) | **Настоящее поле «Что»** на месте нынешнего: тап сразу поднимает клавиатуру. В фокусе под шапкой открывается полноэкранная панель подсказок (портал, `fixed`, от низа шапки до низа экрана в `dvh`). В её верхней строке — чипы «Когда» и «Где» с текущими значениями; чип открывает `Modal` (vaul-шторка на телефоне, диалог от md) с одним полем: календарь на один месяц инлайн или поле адреса. Для ввода адреса в шторке нужен второй тап (Modal намеренно не поднимает клавиатуру на iOS) — принимаем. Когда даты или «Где» выбраны, в поле шапки справа от текста маленький индикатор-точка на иконке календаря |
| Hero главной (есть город) | Большой вариант той же панели над кнопками. Списки — через тот же портал (у секции `overflow-hidden`, абсолютный список обрезался бы). На телефоне — поля столбиком, «Что» открывает ту же панель подсказок |
| `/search`, страницы разделов | Отдельной панели нет: шапка заполнена из адреса. `DateRangeFilter` в верхней полосе остаётся |
| Таб-бар | Без изменений. Тесты TabBar не трогаем |

- **Порталы и слои.** Поповеры «Что»/«Где» — Radix Popover с отменённым
  `onOpenAutoFocus` (фокус остаётся в поле комбобокса), календарь — Radix
  Popover как сейчас у `DateRangeFilter`. Слой `z-50`: выше липкой шапки и
  таб-бара (`z-40`). Ручная проверка 1024/1280 на главной.
- **Без JS и до гидрации.** Форма —
  `<form role="search" action="/search" method="get">`, у поля «Что»
  `name="q"`, скрытые `city`, `from`, `to`, `loc`, `la`, `src`, `lp` (что
  известно из адреса). После гидрации `onSubmit` перехватывает отправку и ведёт
  по `searchSubmitHref`. Мобильное поле — та же форма, поэтому поиск работает
  и без JS. Тест: у формы есть `action`, поля названы.
- **Синхронизация с адресом.** Шапка живёт в корневом layout'е и не
  перемонтируется. Значения полей выводятся из `pathname` + `useSearchParams`
  и пересчитываются при их смене, **если поле сейчас не редактируется** (в
  фокусе). Иначе после ухода с `/search?q=дрель` в шапке висела бы «дрель».
  Тест: ререндер с новыми параметрами обновляет поля.
- **Гео-контекст городов.** Город шапка узнаёт только на клиенте
  (`use-current-city.ts`). Поэтому `Header` (серверный, корневой layout) отдаёт
  `HeaderSearch` не список слагов, а `cities: {slug, name, geo: {region,
  centre: {lat, lon}, token} | null}[]` по всем активным городам. Строится из
  `getActiveCities()` и закэшированного на 60 с чтения `geo_imports` — **без
  загрузки движка**: `token = region + ":" + geo_imports.version`. Hero получает
  ту же запись для своего города со страницы. `geo === null` → «Где» не
  рендерится (§2.5).

**Куда ведёт отправка** — чистая функция
`searchSubmitHref({what, from, to, loc}, {pathname, searchParams, citySlug})` в
`src/lib/search/submit-href.ts`; `page` сбрасывается всегда.

| «Что» | Где мы | Результат |
|---|---|---|
| выбрана подсказка-объявление | любая | канонический путь карточки + `from/to` + «Где» |
| выбран раздел | любая | `/{city}/{root}[/{sub}]` (канонический) + `from/to` + «Где» |
| свободный текст | любая | `/search?q&city&from&to&loc…`; `category`, цена и залог не переносятся |
| «Показать все по «q»» | любая | как свободный текст |
| пусто | `/search` | `/search` без `q`, прочие параметры и фасеты сохраняются, даты и «Где» — из панели |
| пусто | `/{city}…` (город, раздел) | тот же путь, `from/to/loc…` — из панели (пустые удаляются) |
| пусто, есть даты или «Где» | прочие (главная, кабинет…) | `/{city}` + даты и «Где» |
| пусто, нет ни дат, ни «Где» | прочие | навигации нет, фокус в «Что» (как в SP) |

Старый тест `HeaderSearch.test.tsx` «keeps the city even when the query is
empty» (ожидал `/search?city=spb`) заменяется строкой «пусто, ничего нет,
прочие → фокус в «Что»»; без JS та же отправка по-прежнему уходит на
`/search?city=`. После выбора в «Что» фокус переходит на «Когда», как в SP.

### 2.5. «Где» и город (ADR 0012)

- **Регион геоданных.** Геоданные ключуются **регионом**, а не городом. Колонка
  `cities.geo_region varchar(40) NULL` хранит ключ индекса; `krasnodar` и
  `yablonovskiy` оба получают `krasnodar`. Движок и мини-индекс один на регион:
  +80 МБ один раз, а не на каждый город.
- **Центр.** Центр поиска — `cities.lat/lon`. Для обоих реальных городов
  координаты берутся из мест индекса: `Краснодар` (`p_28fa380593fe54`, city) и
  `Яблоновский` (`p_a9ac7554246f38`, town); значения выписываются из файла на
  этапе 3 в `seed_real/cities.csv`.
- **`near` для подсказок адреса** — одно правило везде:
  `выбранная точка ?? сохранённое место того же региона ?? центр текущего
  города (cities.lat/lon)`. Сервер применяет его в `/api/geo/suggest` и
  `/api/geo/reverse` по `city`, если `near` не пришёл; клиент — в
  `suggestNear`, в `suggest` воркера и в `AddressCombobox` формы. Иначе движок
  берёт `ix.center` — самый крупный город индекса (Краснодар), и на
  `/yablonovskiy` «Гагарина 1» (52 улицы «Гагарина») уходит в Краснодар, а
  владелец из Яблоновского выбирает чужую улицу. Тест: `yablonovskiy` без
  `near` → дом в Яблоновском.
- **Админка.** Форма города получает `lat`, `lon` и выбор `geo_region` из
  загруженных (`geo_imports`): новый город настраивается без SQL.
- **Город «Где» не меняет.** Ни `?city=`, ни куку (их меняет только
  `CitySelector`).
- **Выдача с точкой — по региону** (§0 вопрос 1, вариант (а)). Если в адресе
  есть точка и у текущего города есть `geo_region`, фильтр выдачи —
  `listings.city_id IN (активные города этого региона)`; без точки —
  `eq(listings.cityId)`, как сейчас. Счётчики `CategoryTree` и фасетов, индекс
  «Что» для `/search` (`rankListingIds(cityIds)`) и подсказки «Что» (роут
  получает `loc`) следуют тому же набору городов, чтобы R8 держался. Над
  выдачей подпись «Краснодар и рядом». Город в подвале карточки уже есть.
  При ответе (б) — вместо этого счётчик и ссылка на соседний город; при (в) —
  ничего.
- **Город без геоданных** (`geo_region IS NULL` или импорта нет: демо-Казань,
  новый город): **«Где» не рендерится вовсе** — ни в шапке, ни в hero, ни
  чипом на телефоне. Сортировки «Ближе» нет; объявления там имеют
  `geo_precision = 'city'` и расстояний не получают. Пункт «Моё
  местоположение» без расстояний был бы мёртвым контролом.
- **Последнее место.** Хранится в `localStorage` `inrenta_loc` (обёрнут в
  try/catch) вместе с `region`; в городе другого региона игнорируется.
  - Применённым значением «Где» оно **не** становится: поле показывает только
    то, что в адресе страницы, иначе шапка писала бы «Где: ул. …» над
    карточками без расстояний.
  - Оно появляется первой строкой списка «Где» («Недавнее: …», один клик
    применяет) и служит `near` для подсказок адресов.

### 2.6. Параметры адреса

Кодек SP оставляем, но **только точку**: `loc=p:<lat>,<lon>`, `la=<подпись>`,
`src=geo`, `lp=s|t`. `d:`/`o:` не поддерживаются (справочника нет) и, как любой
мусор, превращаются в «без точки». Формат тот же, чтобы тесты SP переносились и
справочник районов можно было вернуть без смены URL.

- **Округление** (§0 вопрос 3): точка пишется с 3 знаками, не с 5, как в SP
  (`SP:geo.ts:242`). Для `src=geo` подпись `la` — улица без номера дома.
- **Точность геолокации.** Если `pos.coords.accuracy > 150` м (десктоп по
  Wi-Fi/IP), ставится `lp=s`, и расстояния идут с «≈». В SP точность
  игнорировалась.
- **Широкое место в «Где»** (город, округ) точки не даёт: выбор означает «весь
  город», `loc` не пишется (как в SP, где у города и округа точки не было).
  См. §2.7, «Точность из подсказки».
- **Переносимые параметры** — `carryParams(sp)` в `src/lib/catalog/filters.ts`
  рядом с `filterParams`: `from, to` (этап 2) и `loc, la, src, lp` (этап 5).
  Кто ими пользуется:
  | Где | Как |
  |---|---|
  | `filterParams` | включает `carryParams` |
  | скрытые поля `ListingFilters` в `CategoryListing` и `SearchResults` | `hidden` строится из `carryParams` плюс контекст страницы (`q, city, category, view, sort`) — иначе «Показать» в фильтрах цены теряет «Где» и `sort=near` |
  | `CategoryTree` (и `CategorySheet`, который его оборачивает) | проп `carryQuery`, дописывается к каждой ссылке раздела |
  | `Breadcrumbs` на страницах города/раздела/объявления | страница дописывает `carryQuery` к `href` крошек |
  | `CategoryFacets` на `/search` | уже строится через `filterParams` — получает автоматически |
  | `ListingCard` | `hrefQuery` |
  | канонические редиректы `[seg]/page.tsx:54` и `[sub]/page.tsx:116` | `canonicalHref(path, sp)` переносит белый список `from, to, qty, loc, la, src, lp` |
  | подсказки «Что» | клиент дописывает к каноническому `href` из ответа |
  | `BookingWidget` | см. §4 |
  `CategoryTiles` и `RecentItems` на главной не меняются: адрес главной дат и
  «Где» не несёт (пустая отправка с ними уходит на `/{city}`).
- **Кто сбрасывает:** `citySwitchHref` сбрасывает `loc…` вместе с датами;
  `datesResetHref` — только даты; крестики «Любые даты» и «×» у «Где» в панели.

### 2.7. Адрес объявления и приватность

**Схема `listings`:**

- `address varchar(200)` — полная подпись, выбранная владельцем (может
  содержать дом). Видит только владелец в форме. `NULL` бывает только у строк до
  backfill.
- `location varchar(120)` — **публичная** подпись без номера дома. Колонку
  оставляем, меняем смысл.
- `lat`, `lon doublePrecision NULL`.
- `geo_precision` — enum `listing_geo_precision` (`house`, `street`, `place`,
  `city`), `NOT NULL DEFAULT 'city'`.

**Точность из подсказки** (`listingPrecision(hit)` в `src/lib/geo/precision.ts`;
общая с точкой пользователя). В индексе Краснодара мест: snt 382,
microdistrict 164, village 87, hamlet 50, town 18, okrug 4, city 1 (проверено
по `index.krasnodar.json`).

| Подсказка | Объявление | Точка «Где» |
|---|---|---|
| `kind=house` с точностью `house` или `interpolated` | `house` | точная |
| `kind=street` или точность `street` | `street`, «≈» | `lp=s`, «≈» |
| `poi` (ЖК, ТЦ) | `place`, «≈» | `lp=t`, «≈» |
| `place` вида microdistrict, snt, village, hamlet, town | `place`, «≈» | `lp=t`, «≈» |
| `place` вида city, okrug | **не принимается**: «Уточните адрес — улица, ЖК, микрорайон или посёлок»; в списке формы такие строки не показываются | точки нет, «весь город» |

Отличие от SP, где POI считается точным: пользователь прямо назвал ЖК
приблизительным. Город и округ — площади в десятки км, «≈ 4 км» до их центра
было бы ложным числом среди настоящих.

**Подпись точности** — `precisionNote` из `SP:address.ts:16-27` переносится и
показывается в момент выбора и под полем: в форме объявления («≈ до улицы —
покупатели увидят приблизительное расстояние», «≈ населённый пункт»; для дома —
«покупатели увидят расстояние до дома, но не номер») и в строках списка «Где».

**Публично показывается** (§0 вопрос 2):

| Место | Что видно |
|---|---|
| Карточка в выдаче | только расстояние «1,2 км» / «≈ 3 км». Адреса нет |
| Страница объявления, `OwnerCard` | `location` — улица / ЖК / пункт **без номера дома** — плюс расстояние, если в адресе есть «Где» |
| JSON-LD, sitemap | без адреса и координат, как сейчас |
| Клиентский HTML / RSC-payload | ни `lat/lon`, ни `address` (см. ниже) |

- **Защита в коде.** Публичные чтения (`CARD_COLUMNS`, `getActiveListingById`)
  выбирают `publicListingColumns` = `getTableColumns(listings)` без `address`,
  `lat`, `lon`; тип — `PublicListing`. Расстояние приходит из SQL готовым числом.
  Полные колонки читают только кабинет и actions.

**Payload адреса** (zod, дискриминированное объединение):

| Вариант | Когда |
|---|---|
| `{mode: "keep"}` | правка, поле адреса не трогали |
| `{mode: "pick", kind, title, subtitle, lat, lon}` | выбрана подсказка (из мини-индекса или с сервера) |
| `{mode: "text", text}` | город без региона, свободный текст 3–200 символов |

Отсутствие ключа `address` → «Форма устарела — обновите страницу» (тот же
приём, что у handover-флагов: `updateListing` пишет `.set()` всеми полями).

**Проверка на сервере** (`resolveListingAddress` в
`src/server/listing-address.ts`; вызывается внутри мутации после проверки
владельца):

- **`keep`.** Action читает текущую строку. Допустимо, только если у неё
  `address IS NOT NULL` и `cityId` не меняется; тогда `address`, `location`,
  `lat`, `lon`, `geo_precision` не пишутся вовсе (остаются как есть). Иначе
  ошибка «Укажите адрес» (новый город или legacy-строка с «Уточните адрес»).
  Правка цены или фото адрес не переспрашивает, переимпорт геоданных её не
  ломает.
- **`pick` в городе с регионом.** Клиентским координатам не доверяем, а id
  хита не используем вовсе: у мини-индекса свои id (`c` + `s0`, `p0`…,
  `SP:client-index.ts:114-116` — «сверять с серверными по title и subtitle»),
  у сервера — `s:…`, `h:…`, и после переимпорта они меняются.
  1. Сервер берёт кандидатов `suggest(title + " " + subtitle, {near: {lat,
     lon}, limit: 10})` ∪ `reverse(lat, lon)`.
  2. Подходит кандидат с тем же `kind`, теми же нормализованными (`normalize`)
     `title` и `subtitle` и точкой не дальше 50 м от присланной. Нет такого —
     «Выберите адрес из подсказок».
  3. Точка, точность, `address` (`hitLabel`) и `location` (`publicLabel`)
     берутся из **серверного** хита. `city`/`okrug` отвергаются (таблица выше).
  4. Если центр города известен, точка должна лежать не дальше 40 км от него.
     Совпадение пункта с городом объявления внутри агломерации не требуется.
  5. Движок недоступен (нет импорта, ошибка загрузки) → «Поиск адресов временно
     недоступен, попробуйте позже». Сохранённая точка **никогда** не
     затирается `NULL` из-за недоступности движка.
- **`text` в городе без региона.** `precision = 'city'`, `lat/lon = NULL`.
  Публичная подпись `location` — текст владельца (как сейчас), с подсказкой
  «без номера дома». В городе с регионом `text` отвергается.
- **`publicLabel(hit, cityName)`:**
  - дом или улица → `"{street}"`, к которому добавляется `", {place}"`, если
    пункт не совпадает с городом объявления (`OwnerCard` сам дописывает город);
  - POI → `title`;
  - место → имя пункта.
- **Форма** (`ListingForm`): поле адреса — `AddressCombobox` с мини-индексом и
  серверными домами, как «Где»; в правке предзаполнено сохранённым `address` и
  отправляет `keep`, пока его не тронули. Смена города сбрасывает поле.

### 2.8. Backfill и сид

- **Скрипт** `scripts/geo-backfill.ts` (`pnpm geo:backfill`), идемпотентный.
  Строки отбираются по `address IS NULL` (в режиме `--db`) или по пустому `lat`
  (в режиме `--csv`). **Запускается только с машины разработчика**: строит
  полный движок в своём процессе (≈ +300 МБ, `SP README:846-848`); для прода —
  через SSH-туннель, как `geo:import`.
- **Геокодирование.** `geocodeDetailed(address || location, {near: центр города,
  strict: false})` в регионе города. Результат (`address`, `location`, `lat`,
  `lon`, `geo_precision`) печатается таблицей «метка → найдено → точность».
  Хиты `city`/`okrug` считаются ненайденными.
- **`--csv seed_real/listings.csv`** дописывает новые колонки в CSV.
  - Запись — новой `stringifyCsv` в `src/lib/csv.ts` (сейчас там только
    `parseCsv`); описания многострочные, с запятыми и кавычками. Тест
    кругооборота: `parse → stringify → parse` на реальном `listings.csv` даёт
    равные строки.
  - Ненайденные выводятся списком, код выхода 1. Оператор правит ячейку
    `address` вручную и запускает повторно.
  - Известные трудные метки (critic A7): `ЮМР` → «Юбилейный», `Западный обход` →
    уточнить по индексу. Двусмысленная `ул. Гагарина` (52 улицы) решается через
    `near` — центр Яблоновского.
  - Таблицу просматривает человек перед коммитом CSV.
- **`--db`** — для строк прода, которых нет в CSV. По порядку выката (§2.9) к
  его запуску строки `seed_real` уже получили адрес из CSV, поэтому
  `address IS NULL` отбирает только их.
  - Ненайденные получают `address = location ?? имя города` и
    `precision = 'city'`, без точки; печатается список.
  - Кабинет показывает у такого объявления «Уточните адрес». Форма правки не
    сохранится без выбора из подсказок (`keep` для них недопустим), но
    объявление не гаснет.
- **Колонки CSV** объявляются и проверяются в `src/lib/seed/rows.ts`, не в
  скрипте:
  - `LISTING_COLUMNS` + `address, lat, lon, precision`; `CITY_COLUMNS` +
    `geo_region` (`lat, lon` там уже есть).
  - Валидатор: `lat/lon` парой и в диапазоне; `precision` из enum; `location`
    ≤ 120 (как и сейчас, «синхронно с формой»). Если у города в `cities.csv`
    есть `geo_region`, а у объявления `lat` пуст, — ошибка с подсказкой
    запустить `pnpm geo:backfill --csv`: иначе повторный сид стёр бы точки.
  - `scripts/seed-real.ts` пишет новые поля и учитывает их в `differs()`.
  - Тесты — `tests/lib/seed-rows.test.ts`.
- **`seed_real/cities.csv`.** Колонки `lat,lon` заполнены, новая — `geo_region`.
- **Демо `scripts/seed.ts`** (Казань): `address = 'Казань'`, `precision = 'city'`.

### 2.9. Геоданные: схема, загрузка, деплой

- **Обмен данными.** Контракт — JSON `GeoIndexData`
  (`SP:src/lib/geocoder/types.ts`). Проверено: файл
  `sravniprokat/data/geocoder/build/index.krasnodar.json` (79,8 МБ, 2026-09-30)
  в нём уже есть; id мест — строки вида `p_28fa380593fe54`. Схему SP 1:1 не
  берём: колонки `bounds`, `osm_ref`, `gar_guid`, `name_key`, `number_norm` и
  `source` у мест, улиц и POI рантайм не читает, а в JSON их нет.
- **Таблицы inrenta** — ровно то, что читает загрузчик. Ключ — `region`, FK на
  `cities` нет:
  - `geo_places(id, region, kind, name, aliases, parent_id, lat, lon)`
  - `geo_streets(id, region, place_id, name, type, aliases, lat, lon, houses, line)`
  - `geo_houses(id identity, region, street_id, place_id, number, lat, lon,
    precision, source, postcode)`. Порядок вставки = порядок JSON, а он уже
    отсортирован выгрузкой SP по `street_id, number_norm`.
  - `geo_pois(id, region, name, kind, aliases, place_id, lat, lon, address)`
  - `geo_imports(id, region, version, built_at, counts)`
  - Индексы — **составные `(region, id)`**: загрузчик движка читает регион с
    `order by id`, и с одним `region` 469 тыс. домов сортировались бы на диске.
    FK между гео-таблицами нет: замена идёт целиком, и целостность держит импорт.
- **Загрузчик** `scripts/geo-import.ts` (`pnpm geo:import <file> [--region
  krasnodar]`).
  - Одна транзакция: удалить строки региона → вставить пачками → строка
    `geo_imports` с `version` и `builtAt` из файла.
  - Пачки — многострочный `insert … values` drizzle с размером
    `floor(65535 / число колонок)` (лимит параметров Postgres). Не `unnest`:
    колонку `aliases text[]` так построчно не передать — массив массивов в
    Postgres обязан быть прямоугольным, а `unnest` разворачивает его целиком.
  - Повторный запуск того же файла даёт то же состояние.
- **Dev.** `pnpm db:migrate` → `pnpm db:seed:real` →
  `pnpm geo:import sravniprokat/data/geocoder/build/index.krasnodar.json`
  (путь только как аргумент; код из SP копируется, импортов из папки SP нет).
- **Прод** (DEPLOY):
  - `geo:import` и `geo:backfill --db` — только с машины разработчика через
    SSH-туннель к прод-Postgres: оба строят сотни МБ в Node, на 1 ГБ VPS рядом с
    живым `app` их не запускаем.
  - После `geo:import` — `docker compose restart app`: иначе app подхватит
    новую версию, ещё держа старый движок (пик ≈ +280 МБ поверх ≈ 80 МБ).
  - Порядок выката:
    1. деплой этапа 3;
    2. `geo:import` (туннель) → `restart app`;
    3. центры и `geo_region` городов (CSV → `db:seed:real` на сервере, как в
       DEPLOY §«Реальные данные», или админка);
    4. деплой этапа 4;
    5. `db:seed:real` на сервере с CSV, где уже есть `address/lat/lon/precision`
       (проверенные человеком точки для 61 объявления);
    6. `geo:backfill --db` (туннель) — только оставшиеся строки.
- **Аварийный выключатель** (R3): `cities.geo_region = NULL` в админке. Город
  становится «без геоданных»: «Где» прячется, новый адрес вводится текстом,
  `keep` сохраняет прежние точки. Затем `restart app`, чтобы движок не грузился.
- **Обновление данных** — вручную. Конвейер SP → `db:export-geo` → JSON →
  `geo:import`. Крона нет, правило не нарушается.
- **Бэкап.** Гео-таблицы остаются в дампе (без особых случаев). В RECOVERY число
  таблиц заменяется командой.
- **Память, 1 ГБ.**
  - Геокодер: ≈ +80 МБ RSS постоянно и ≈ +280 МБ пиком ~15 с при загрузке
    (цифры SP, на inrenta не мерены).
  - **Когда грузится.** Лениво: первый запрос к `/api/geo/*` или к
    `client-index`, первая мутация адреса. Рендер страниц движок **не** трогает:
    токен мини-индекса берётся из `geo_imports.version` (§2.4), а не из
    `addressIndexToken` SP, который строит индекс. Клиент запрашивает

## 3. Расстояние

- **SQL** (`distanceKm(point)` в `src/server/catalog.ts`): гаверсинус, тот же,
  что `haversineKm` в JS. Сравнение с JS-реализацией — в тестах.

  ```sql
  case when l.lat is null then null else
    2 * 6371 * asin(least(1, sqrt(
      power(sin(radians(l.lat - $lat) / 2), 2)
      + cos(radians($lat)) * cos(radians(l.lat)) * power(sin(radians(l.lon - $lon) / 2), 2)
    ))) end
  ```

- **Индекс не нужен.** Радиуса нет, а выражение считается по строкам города
  (или региона), которые уже отобраны по `city_id/status`. bbox и btree по
  `lat` появятся вместе с фильтром по радиусу (BACKLOG).
- **Колонки.** `cardColumns(near?)` = `CARD_COLUMNS` плюс `distanceKm` и
  `listingPrecision`. `ListingWithOwner` получает `distance: {km, approx} | null`.
- **Строки без точки** (`city` или legacy) получают `NULL`. В сортировке «Ближе»
  они идут последними (`NULLS LAST`, затем `id`) и расстояния не показывают.
- **Правило «≈»:** `approx = точка пользователя приблизительная (lp=s|t) ИЛИ
  geo_precision у объявления ≠ 'house'`.
- **Подпись** — `distanceLabel(km, approx)` в `src/lib/geo/distance.ts`:

  | Случай | Подпись |
  |---|---|
  | приблизительно | `≈ {max(1, round(km))} км` |
  | точно, < 1 км | `{max(100, round(km·10)·100)} м` |
  | точно, 1–10 км | `{km, один знак, ru-RU} км` («1,2 км») |
  | точно, ≥ 10 км | целые км |

  Расстояние по прямой. `title` у подписи — «по прямой».
- **Подвал карточки на телефоне.** В сетке `grid-cols-2` карточка ≈ 159 px при
  ширине 360, контента ≈ 135 px. Правило: расстояние `shrink-0`, способ
  получения `min-w-0 truncate`; ниже `sm`, когда расстояние есть, оно
  **заменяет** город (город виден на странице объявления и в подписи над
  выдачей), от `sm` — «1,2 км · Яблоновский», город `min-w-0 truncate`. То же
  в строке списка (`ListingCard.tsx:192-200`). Тест в `ListingCard.test`.
- **Сортировка `near` («Ближе»)** доступна, только когда в адресе есть точка и у
  города есть регион. Иначе её нет в меню, а `sort=near` из адреса молча
  отбрасывается.
- Остальные сортировки и пагинация не меняются. Расстояние при них просто
  выводится.
- **Минуты в пути не показываем** (§1).

## 4. Даты

- **Пикер: остаёмся на `react-day-picker`** (§0 вопрос 4). Сетку SP не
  переносим: у неё нет навигации стрелками и неверный `role="grid"`. У DayPicker
  уже есть клавиатура, ARIA и тема `.rdp-theme` на токенах (ochre = занято,
  hover = `--color-hover`). Из SP берём взаимодействие:
  - два клика в любом порядке;
  - превью диапазона под курсором;
  - строка статуса `aria-live`;
  - два месяца в поповере шапки на `lg`;
  - автозакрытие через 220 мс после второго клика.
- **Общий выбор диапазона.** Чистая функция `pickRange(sel, day)` в
  `src/lib/booking/range-pick.ts`, **без капа длины** (в SP был кап
  `MAX_RENTAL_DAYS`; здесь границей служит только горизонт пикера). Её
  используют поле «Когда» и `BookingWidget.onDayPick`; поведение `touched`
  остаётся в виджете.
- **Один выбранный день** при отправке даёт `from = to = день` — однодневная
  аренда, валидная по правилу «обе границы включены».
- **`DateRangeCalendar`** выносится из `DateRangeFilter` в
  `src/components/catalog/DateRangeCalendar.tsx`. Пропсы: `months: 1 | 2`,
  `autoClose: boolean`, `today` (обязателен), `onCommit`. Блокирует дни до
  `today` и после `today + 180`.
  | Потребитель | months | autoClose | Фиксация |
  |---|---|---|---|
  | «Когда» в шапке, `lg` | 2 | да | закрытие поповера; отправка — кнопкой поиска |
  | «Когда» в шторке на телефоне | 1 | нет | «Готово» |
  | `DateRangeFilter` на выдаче | 1 | нет | «Показать» и «Сбросить» — как сейчас, ширина `w-[19rem]` сохраняется |
  Число месяцев задаёт потребитель по контейнеру, а не `useIsDesktop` (иначе
  в диалоге md–lg рисовались бы два месяца в узком окне).
- **Сброс в панели:** «Любые даты» в поповере «Когда», «×» в поле «Где».
- **`today` на клиенте.** «Когда» в шапке и hero считает `today` через
  `todayStr()` (зона Europe/Moscow, ADR 0013) **при открытии** поповера, а не
  берёт из пропа корневого layout'а: шапка не перерисовывается, и после
  полуночи открытая вкладка разрешила бы вчерашний день.
- **Семантика inrenta** (обе границы включены):
  - число дней — `rentalDaysCount`;
  - подпись «сб 12 — пн 14 окт · 3 дня» (`ruPlural` день/дня/дней);
  - строка статуса: «Выберите первый день» → «С 12 окт — выберите последний
    день». Слов «день возврата» нет.
  - `nights` из SP (`rentalDays`) не переносим.
- **Хелперы** в `src/lib/catalog/dates.ts`: `isDateStr`, `weekdayShort`,
  `dateRangeLabel`, `daysLabel` (строка→строка, UTC, как требует 0013).
  `localToday` из SP не нужен — есть `todayStr`.
- **Строгий разбор дат:**
  - `isDateStr` — регэксп плюс обратный ход
    `new Date(s+"T00:00:00Z").toISOString().slice(0,10) === s`. 30 февраля
    отвергается.
  - `assertDateString` (`availability.ts`) переходит на `isDateStr`. Это касается
    и брони.
  - `parseDateRange(sp, today)` → `parseFilters(sp, today = todayStr())`:
    - обе границы валидны и `from ≤ to`, иначе фильтра нет;
    - `to < today` → фильтра нет;
    - `from > today + 180` или `to > today + 180` → фильтра нет (как и любой
      половинчатый диапазон — правило domain.md «только целиком»; пикер такой
      диапазон не даёт);
    - `from < today` → `from = today` (прошедшие дни забронировать нельзя, так
      что смысл фильтра не меняется). Это единственный кламп; он записывается
      в domain.md как исключение;
    - максимальной длины нет, как в брони.
  - **UI видит нормализованный диапазон.** `DateRangeFilter`, шапка, `carryParams`
    и `filterParams` берут `from/to` из результата `parseFilters`, а не сырой
    query: человек видит те же даты, что применены.
- **Даты доходят до карточки объявления.**
  - `ListingCard` получает `hrefQuery` (§2.6).
  - Канонические редиректы переносят белый список (§2.6). Метаданные canonical
    по-прежнему без query.
  - Виджет брони читает `?from&to` (`page.tsx:198-205`).
  - **`BookingWidget` больше не стирает чужие параметры.** Сейчас на монтировании
    он делает `replaceState(pathname + buildBookingQuery(sel))`
    (`BookingWidget.tsx:89-94`) и выбрасывает всё, кроме `from/to/qty`, — то
    есть `loc/la/src/lp`, а с ними расстояние в `OwnerCard` при перезагрузке,
    в «поделиться» и в `callbackUrl` входа. Теперь он берёт
    `window.location.search`, заменяет в нём только `from/to/qty` (удаляя их
    при умолчании) и оставляет остальное. Тест: «`loc` переживает выбор дат и
    попадает в `callbackUrl`».
- **Свобода на карточке.** При выбранном диапазоне `SearchResults` и
  `CategoryListing` грузят `getAvailabilityRows(ids, from, to)` вместо
  today…today+6. `ListingCard` считает `min freeQty` по дням диапазона: зелёный —
  свободно всё, охра — часть.
  - Без диапазона — сегодня, как сейчас.
  - Отфильтрованная выдача поэтому больше не показывает «Занято» из-за
    сегодняшнего дня.
  - Мини-календари связанных объявлений на странице объявления не меняются.
