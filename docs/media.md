# Изображения

Единственный тип загружаемых файлов — картинки. Потребителя три: фотографии
объявлений, обложка профиля и аватарка. Путь у всех один.

## Пайплайн загрузки

```
файл из формы
   → POST /api/upload (multipart, поле "image")
   → детект настоящего MIME по сигнатуре файла
   → sharp: rotate → resize → webp
   → PutObject в S3
   → строка в таблице uploads
   → { url, width, height } обратно в форму
```

Код: `src/app/api/upload/route.ts`, `src/lib/images/`, `src/lib/storage/`.

## Проверки на входе

Порядок в `route.ts`, каждая проверка возвращает свой код ошибки:

| Проверка | Ответ |
|---|---|
| хранилище не настроено (`STORAGE_ENDPOINT` пуст) | `503 storage_not_configured` |
| нет сессии | `401 unauthorized` |
| пользователь забанен | `403 banned` |
| `Content-Length` или размер файла больше 10 МБ | `413 too_large` |
| тело не является формой / нет поля `image` | `400 bad_form` / `400 no_image` |
| тип файла не распознан или не разрешён | `415 bad_mime` |
| sharp не смог обработать | `500 normalize_failed` |
| S3 не принял объект | `500 r2_failed` |
| не удалось записать в БД | `500 db_failed` |

Забаненного отсекают отдельно: интерфейсы ему закрыты, но ручка доступна по
сети напрямую.

**MIME определяется по содержимому**, а не по заголовку из браузера
(`file-type` читает сигнатуру). Принимаются `image/jpeg`, `image/png`,
`image/webp`, `image/gif`. HEIC с айфонов не поддерживается — см.
[BACKLOG.md](BACKLOG.md).

## Нормализация

`src/lib/images/normalize.ts`, порядок операций важен:

1. `.rotate()` — читает EXIF orientation и физически поворачивает пиксели,
   после чего EXIF отбрасывается (заодно уходят геометки).
2. `.resize({ width: 2560, height: 2560, fit: "inside", withoutEnlargement: true })`
   — вписывает в квадрат 2560×2560, сохраняя пропорции; мелкие картинки не
   растягиваются.
3. `.webp({ quality: 85 })` — без флага `animated`, поэтому у анимированного
   GIF берётся первый кадр.

На выходе всегда webp. Реальные размеры перечитываются из результата и уходят в
БД — по ним `next/image` резервирует место и не даёт скачка вёрстки.

## Хранение

- Ключ объекта: `uploads/{userId}/{ulid}.webp`.
- Публичный адрес: `{STORAGE_PUBLIC_BASE}/{key}`.
- `Cache-Control: public, max-age=31536000, immutable` — имя файла содержит
  ULID и никогда не переиспользуется.
- Клиент S3 — `@aws-sdk/client-s3` (`src/lib/storage/r2.ts`). Имена
  `getR2Client` / `r2Bucket` исторические: изначально планировалась Cloudflare
  R2, фактически используется S3 Timeweb. Переименование — отдельная задача, на
  поведение не влияет.

Каждая успешная загрузка оставляет строку в таблице `uploads` (`userId`, `key`,
`publicUrl`, `mime`, `size`, `width`, `height`). Эта таблица служит не только
реестром, но и **белым списком**: см. ниже.

`next/image` пускает картинки только с известных хостов — список собирается в
`next.config.ts` из фиксированных доменов аватарок OAuth и хоста
`STORAGE_PUBLIC_BASE`. Условий на самом деле два: хост в списке и адрес не
приватный — про второе см. [testing.md](testing.md).

## Фотографии объявления

Компонент `PhotoDrop` (`src/components/cabinet/`) грузит файлы через
`/api/upload` и складывает результат в `photosJson` объявления — массив
`{ url, width, height }`. Показывает их `Gallery` на карточке товара.

Удаление файла из S3 при снятии фото с объявления не делается: строка в
`uploads` и объект в бакете остаются. Осознанное упрощение — объекты дешёвые, а
удаление требует сверки, что картинка больше нигде не используется.

## Обложка профиля

Широкая картинка над шапкой кабинета и над публичной витриной продавца, поле
`users.cover_url`. Рекомендуемая пропорция 4:1.

Два источника:

1. **Пресет** — готовая картинка из `public/covers/`. Список в
   `src/lib/covers.ts` (`COVER_PRESETS`), адреса вида `/covers/lenta.svg`.
2. **Своя загрузка** — тот же `/api/upload`, адрес в S3.

Правила из `src/lib/covers.ts`:

- `NULL` в `cover_url` означает «дефолтный пресет» — первый в списке. Так смена
  дефолта в будущем подхватится у всех, кто ничего не выбирал.
- `isCoverPreset(url)` — белый список для server action.
- `resolveCoverUrl(url)` — что показывать. Адрес под `/covers/`, которого больше
  нет в списке (список меняли после того, как человек выбрал), тихо падает на
  дефолт вместо битой картинки.

### Почему обложку нельзя подменить

`updateCover` (`src/server/actions/profile.ts`) не принимает адрес на веру:
либо это пресет из белого списка, либо строка в `uploads`, у которой
`publicUrl` совпадает с присланным **и** `userId` равен текущему. Иначе в поле
можно было бы положить что угодно — вплоть до чужой картинки с трекером.

После смены обложки инвалидируются layout'ы личной зоны (`/cabinet`,
`/profile`) и публичная страница `/u/{id}`.

Кроппер 4:1 при загрузке и сброс обложки из админки — осознанно отложены, см.
[BACKLOG.md](BACKLOG.md).

## Аватарка

Поле `users.image`. Заполняется двумя способами: провайдером при первом входе
через Яндекс или VK — и самим человеком.

Записать её может только владелец, из кабинета (камера на аватарке в шапке) или
из настроек `/profile`. Убрать — тоже: `NULL` означает «нарисовать кружок с
первой буквой имени», это делает `Avatar` (`src/components/ui/`).

Для тех, кто входил через провайдера, «убрать» необратимо: адаптер Auth.js пишет
профиль только при создании пользователя и на повторных входах `image` не
обновляет. Интерфейс предупреждает об этом до нажатия.

### Кадрирование происходит в браузере

`AvatarCropper` (`src/components/account/`) декодирует выбранный файл, даёт
подвигать и приблизить кадр и отдаёт готовый квадрат 1024×1024 через `canvas`.
В `/api/upload` уезжает уже он — **отдельного режима у ручки нет**: квадрат
меньше 2560 проходит через `resize({ fit: "inside", withoutEnlargement: true })`
не меняя размеров.

Три вещи, которые ломаются, если делать наивно:

- **EXIF.** Кадрируют до сервера, поэтому `sharp.rotate()` уже не спасёт:
  декодирование идёт через `createImageBitmap(file, { imageOrientation:
  "from-image" })`, запасной путь — обычный `<img>`, к которому браузер
  применяет ориентацию сам. Показ и экспорт берут **один и тот же**
  декодированный источник: иначе на фото с поворотом 90° в файл уедет не тот
  кадр, что видел человек.
- **Жесты внутри окна.** На мобиле окно — лист снизу с собственной прокруткой,
  поэтому вьюпорту нужен `touch-action: none`. Колесо мыши слушается вручную
  (`{ passive: false }`): React вешает `wheel` на корень пассивно, и
  `preventDefault()` из `onWheel` не сработал бы.
- **webp в `toBlob` есть не везде.** Старый Safari молча отдаёт PNG. Так и
  отправляем: PNG в `ACCEPTED_MIME` есть, а `normalizeToWebp` приведёт его к
  webp сам.

Математика кадра вынесена в `src/lib/images/crop-geometry.ts` — без DOM, под
тестом: она решает, какие пиксели попадут в файл, и ошибку в ней видно только
на границах.

Загрузка уходит **один раз, по «Сохранить»**, а не на выбор файла: старые
объекты из S3 не удаляются никогда (см. ниже), и промежуточные кадры оседали бы
в хранилище мусором.

### Почему аватарку нельзя подменить

`updateAvatar` (`src/server/actions/profile.ts`) проверяет адрес тем же
способом, что и обложка: строка обязана быть в `uploads` с этим `publicUrl`
**и** с `userId` текущего пользователя. Пресетов у аватарки нет — либо своя
загрузка, либо `NULL`.

Инвалидируются layout'ы личной зоны (`/cabinet`, `/profile`,
`/chat` — там каркас рисует героя со своей аватаркой) и `/u/{id}`. Полного
покрытия нет: своя аватарка висит ещё на карточках выдачи списком и в блоке
владельца на страницах товара. Все они `force-dynamic`, поэтому вызов чистит
фактически клиентский Router Cache того, кто менял, — остальные получают свежую
на следующем запросе и так.

Хедеру и таб-бару инвалидация не нужна вовсе: они читают `session.user.image`, а
database-сессии берут пользователя из БД на каждый запрос.

### Просмотр

`AvatarViewer` (`src/components/ui/`) открывает аватарку на весь экран. Стоит
только на крупных — в шапке кабинета и на публичной странице продавца; в
хедере, таб-баре и списке переписок аватарки остаются обычным `Avatar`, потому
что клик там уже занят навигацией. Без `src` viewer вырождается в `Avatar`:
у буквенного кружка нечего показывать.

## Локальная разработка

Без `STORAGE_*` загрузка не работает: `/api/upload` отвечает 503. Это нормальное
состояние локального окружения — проверять пайплайн вживую нужно на окружении с
настроенным S3. Пресеты обложек при этом работают: они лежат в `public/` и в S3
не ходят.

`pnpm db:seed` раздаёт демо-владельцам разные пресеты обложек, чтобы витрины не
выглядели пятью копиями дефолта.

## Фотографии сида

Витринные объявления из `seed_real/` живут в том же бакете, что и
пользовательские загрузки, но под префиксом `seed/`, а не `uploads/`. Кладёт их
туда `pnpm seed:photos`: берёт исходники из `seed_real/Фото/`, гонит через тот
же `normalizeToWebp` и `detectMime`, что и `/api/upload`, и записывает манифест
`seed_real/photos.json` — имя файла → ключ объекта и размеры.

Манифест едет в git, исходники — нет. Поэтому наполнение базы
(`pnpm db:seed:real`) не требует ни снимков на диске, ни доступа к бакету:
адреса собираются из ключа и `STORAGE_PUBLIC_BASE`. Готовый URL в манифест не
пишется намеренно — база у локального MinIO и у прода разная, а манифест один.
