# 0022. Индекс поиска «Что» — в памяти процесса `app`, подсказки — GET-роутом

## Status

Accepted (2026-10-03)

## Context

Поиск был одной строкой с ILIKE по названию и описанию, без подсказок. Опечатка,
другая раскладка («gthajhfnjh»), транслит, бытовое имя вещи («болгарка» при
заголовке «УШМ Makita») или слово про раздел («дача») не находили ничего.

Механика умного поиска уже была в соседнем проекте sravniprokat (SP):
нормализация, раскладка, транслит, гомоглифы, основа слова, нечёткое совпадение,
подмножества слов при нуле, подсветка. Её переносим, а не пишем заново. Отличие в
данных: SP ищет по курируемому каталогу на ~12 КБ, а здесь ищем по
пользовательским заголовкам, число которых растёт вместе с маркетплейсом.

Требования:

- подсказки на каждое нажатие, p95 < 30 мс на 10 тыс. объявлений;
- верх `/search` без фасетов совпадает с подсказками (иначе подсказка обещает
  одно, а «Найти» показывает другое);
- скрытое, архивное и забаненное не подсказывается: подсказка не должна вести на
  404;
- правка владельца видна в подсказках сразу.

## Decision

**Индекс живёт на сервере, в памяти процесса `app`.** `src/server/search-index.ts`
собирает его одним запросом по активным объявлениям набора городов (join
разделов, без забаненных владельцев и отключённых городов) и держит на
`globalThis.__inrentaSearchIndex`. `globalThis`, а не переменная модуля: роут
подсказок, страницы и server actions могут оказаться в разных бандлах со своей
копией модуля, а сбрасывать правка обязана тот же кэш, из которого отвечает
роут. Ключ кэша — отсортированный набор id городов; сейчас это всегда один
город. Параллельные запросы ждут одну сборку.

**Скоринг — чистая функция в `src/lib/search/`**, перенос SP без изменения
поведения. Запись объявления — три поля: заголовок, раздел (имя, корень,
`keywords` раздела) с меньшим весом и начало описания с ещё меньшим, только по
началу слова и основе, без нечёткого совпадения. Каждое слово запроса обязано
совпасть. Названия активных городов в обоих падежах — стоп-слова, снимаются из
`cities` в момент сборки. Синонимы (`src/lib/search/synonyms.ts`) и `keywords`
разделов (`src/lib/seed/categories.ts`) лежат в коде: синонимы — равнозначные
названия одной вещи, `keywords` — слова про раздел целиком, потому что их
совпадение получает каждое объявление раздела.

**Словарь вместо перебора.** Слова всех записей сведены в словарь уникальных слов
города с постингами: слово запроса сравнивается с каждым уникальным словом один
раз, оценка расходится по записям. Результат тот же до бита, что у наивного
перебора SP, — это проверяет `tests/search/listing-index.test.ts`.

**Выдача — подсказки плюс хвост.** Подсказкой объявление становится, только если
все слова совпали в заголовке или разделе. `/search` (`rankListingIds` в
`src/server/search.ts`) берёт ровно эти совпадения в том же порядке, а после них
— совпавшие только по описанию. Один общий порядок по оценке не годился:
совпадение по описанию могло обогнать опечатку в названии раздела, и верх
выдачи разошёлся бы с подсказками. Если запрос из двух и более слов не нашёл
ничего, выдача берёт ту часть запроса, у которой самое сильное первое
совпадение, и говорит об этом плашкой; в подсказках подмножеств нет.

**У запроса есть потолок.** Скоринг синхронный и идёт на общем потоке `app`:
каждое слово запроса сравнивается со всем словарём города, а у `/search` нет
лимитера. Поэтому ищутся не больше `MAX_QUERY_WORDS` слов из первых
`MAX_QUERY_LENGTH` знаков (`src/lib/search/match.ts`) — и в выдаче, и в
подсказках. Подмножества при нуле делят один кэш оценок слова: словарь по
каждому слову просматривается один раз на запрос, а не на каждое подмножество.

**SQL получает готовый набор id.** `searchListings` и `getSearchFacets`
фильтруют `inArray(listings.id, ids)`, а сортировка «Подходящие» —
`array_position` по тому же массиву, переданному одним параметром. Фильтры,
даты, фасеты, счёт и страницы остаются в SQL. Если индекс собрать не удалось,
выдача уходит на прежний ILIKE с `console.error` — других ролей у ILIKE нет.

**Подсказки — GET-роут `/api/search/suggest`, а не Server Action.** Action — это
POST, клиент выполняет их очередью и не кэширует, а подсказкам нужны
параллельные кэшируемые запросы. Ответ — канонические пути карточек и разделов
без query, `Cache-Control: private, max-age=30`, лимит `search` по IP. На
клиенте (`src/components/search/suggest-client.ts`) — дебаунс, LRU-кэш ответов
со сроком как у `max-age` (кэш живёт со вкладкой, а индекс меняется), общий
запрос для одинаковых и сверка порядка: устаревший ответ не перетирает свежий.

**Свежесть — в два контура.**

1. Явный `invalidateSearchIndex()` из мутаций, которые меняют состав или тексты
   индекса: объявления, бан и разбан, разделы, города. Сбрасываются все города
   разом. Где именно вызывается:

   ```bash
   grep -n "invalidateSearchIndex" src/server/actions/*.ts
   ```

2. Версия набора — `count(*)` и `max(updated_at)` активных объявлений, сверка не
   чаще раза в `VERSION_TTL_MS`. Она ловит то, что прошло мимо мутаций: сиды,
   правки из другого процесса, кэш, который не оказался общим.

Сборка, начатая до инвалидации, в кэш не попадает.

## Замер

Разовый скрипт вне репозитория, только скоринг из `src/lib/search` — без БД и
HTTP. Node v24.15, синтетические объявления на реальном дереве разделов:
заголовок из прилагательного, вещи, бренда и модели, описание из 30–90 слов, в
индекс идут первые 50. На 10 тыс. объявлений в словаре 7 670 уникальных слов
заголовков и разделов и 19 470 слов описаний. Запросы — префиксы слов по мере
набора, опечатки, другая раскладка, синонимы, бренды, многословные.

| | 10 тыс. | 30 тыс. |
|---|---|---|
| подсказка p50 / p95 / max (50 объявлений + разделы) | 2,0 / 5,4 / 6,8–18 мс | 5,4 / 14,2 / 18 мс |
| выдача `/search` p50 / p95 / max (до 1000, с подмножествами) | 2,0 / 5,5 / 19–26 мс | 5,5 / 14,8 / 53 мс |
| сборка индекса | ≈ 127 мс | 356 мс |
| куча индекса после GC, без строк | 10,5 МБ | 23,7 МБ |
| куча строк (с описаниями) | 13,8 МБ | 41 МБ |
| RSS процесса | 168–183 МБ | 292 МБ |

Бюджет 30 мс выполнен с запасом. Строки в замере держат описания целиком;
сервер после сборки описания из строк выбрасывает, так что в `app` они легче.
RSS — голого процесса Node со сгенерированными данными, а не `app`.

## Consequences

- **Потолок выдачи — 1000 совпадений** (`RESULTS_LIMIT` в
  `src/server/search.ts`). Это граница схемы: SQL фильтрует, считает и листает
  только внутри этой тысячи. У запроса, который совпал с большим числом
  объявлений, счётчик не больше тысячи, а фильтр цены или залога отбирает из
  лучших по релевантности, а не из всех совпавших.
- **Память растёт с каталогом.** Индекс — по одному на город, весь каталог в
  `app`. Процессов в проде два, и `realtime` индекса не держит; при нескольких
  экземплярах `app` у каждого был бы свой индекс, и явная инвалидация сбросила
  бы только свой — остальные догоняли бы по версии.
- **Инвалидация грубая.** Любая правка объявления сбрасывает индексы всех
  городов, и следующий запрос в каждом городе платит полную сборку (см. замер).
  Пока правок мало, это дешевле точечного обновления.
- **Без инвалидации подсказка отстаёт не больше чем на `VERSION_TTL_MS`.**
  Переименование раздела или города версию не меняет и ловится только явной
  инвалидацией. Скрытое объявление устаревший индекс в выдачу `/search` не
  вернёт — SQL поверх id по-прежнему требует `status = 'active'`, — а новое
  появится в ней, как и в подсказках, только после пересборки.
- **Синонимы и `keywords` правятся только кодом.** Раздел, заведённый в
  админке, ключевых слов не имеет, пока их не впишут в
  `src/lib/seed/categories.ts`.
- **Подсказки пока не учитывают даты.** Поля «Когда» в панели нет, и роут
  `from`/`to` не читает. Когда оно появится, занятость проверяется SQL-ом по
  верхним кандидатам индекса — так подсказки останутся согласованы с выдачей при
  выбранных датах.
- `NEEDS REVIEW`: что кэш на `globalThis` действительно один для роута, страниц
  и actions в standalone-сборке, проверено только тестами, не на prod-сборке.
  Если он окажется не общим, правка владельца дойдёт до подсказок не сразу, а
  через сверку версии.

## Alternatives considered

**Индекс на клиенте, как в SP.** Там клиенту уходит каталог на ~12 КБ. Здесь при
10 тыс. объявлений это мегабайты JSON на каждую страницу и линейный скоринг на
телефоне на каждое нажатие.

**SQL: `pg_trgm` или полнотекстовый поиск Postgres.** Раскладку, транслит,
гомоглифы и основу слова SP пришлось бы переписать на SQL, и ранжирование
подсказок разошлось бы с ранжированием выдачи. Это путь на тот случай, когда
индекс перестанет помещаться в память, — см. [BACKLOG](../BACKLOG.md). Есть ли
`pg_trgm` в образе `postgres:16-alpine`, не проверялось.

**Server Action для подсказок.** Отвергнут выше: очередь и отсутствие кэша.

**Один порядок по оценке для выдачи.** Отвергнут выше: описание обгоняло бы
опечатку в названии, и верх выдачи не совпадал бы с подсказками.
