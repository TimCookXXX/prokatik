# Архитектура

Как устроено приложение и где проходят границы между слоями. Документ описывает
фактическое состояние кода; при расхождении прав код.

## Общая картина

Next.js 16 (App Router) в режиме fullstack: один процесс отдаёт и HTML, и
мутации. REST API для фронтенда нет — данные приезжают в Server Components
напрямую из базы, а изменения идут через Server Actions.

Рядом стоит **второй процесс, `realtime`** — доставка сообщений и уведомлений
вебсокетом (см. [0009](decisions/0009-realtime-as-a-separate-process.md)).
Отдельный он вынужденно: кастомный сервер несовместим с `output: "standalone"`,
а route handlers не дают доступа к `upgrade`. Общаются процессы только через
Postgres — прямых вызовов между ними нет.

```
Браузер
  │
  ├── GET  → middleware (edge) → Server Component → src/server/*.ts → Drizzle → Postgres
  │                                    │
  │                                    └── src/lib/** (чистая логика)
  │
  ├── POST (Server Action) → src/server/actions/*.ts → транзакция → revalidatePath
  │                                                        │
  │                                                        └── pg_notify (последним оператором)
  │                                                                   │
  └── WS /ws → realtime/server.ts ←──────── LISTEN ──────────────────┘
                   │
                   └── Map<userId, Set<socket>> → кадр в браузер (без тела сообщения)
```

Событие пишется в ту же транзакцию, что и данные, поэтому обогнать их не может.
`NOTIFY` при этом не персистентен: всё, что случилось в разрыве, потеряно — после
восстановления слушателя клиентам уходит широковещательный `resync`, и они
дочитывают дельту сами.

HTTP-роуты (`src/app/api/**`) существуют только там, где Server Action
принципиально не подходит: OAuth-редиректы, переход по ссылке из письма,
multipart-загрузка файла, healthcheck, подсказки поиска
(`/api/search/suggest`) и адресов (`/api/geo/suggest`, `/api/geo/reverse`,
`/api/geo/client-index`). Подсказкам нужны параллельные кэшируемые GET на
каждое нажатие, а Server Action — это POST, который клиент выполняет очередью
и не кэширует ([0022](decisions/0022-search-index-in-app-memory.md),
[0021](decisions/0021-own-geocoder-and-listing-coordinates.md)).

## Слои

| Слой | Где | Отвечает за | Чего не делает |
|---|---|---|---|
| Роуты и страницы | `src/app/**` | URL, резолв слагов, метаданные, композиция UI | не ходит в Drizzle напрямую |
| Read-слой | `src/server/*.ts` | запросы на чтение, форма данных для страниц | не мутирует, не рендерит |
| Мутации | `src/server/actions/*.ts` | Server Actions: валидация, транзакции, инвалидация кеша | не содержит чистой доменной логики |
| Доменная логика | `src/lib/**` | правила без БД: даты, занятость, статусы, валидация, auth-флоу | не знает про Next и Postgres |
| Инфраструктура | `src/lib/{db,env,storage,mail,rate-limit}` | подключения, конфигурация, внешние сервисы | не содержит бизнес-правил |
| UI | `src/components/**` | презентация | не ходит в БД |
| Схема | `drizzle/schema.ts` | единственное описание таблиц | — |
| Оформление и тексты | `theme/**` | токены, шрифты, строки интерфейса, SEO-дефолты | — |

Направление зависимостей одностороннее: `app → server → lib → db`. Обратных
импортов нет: `src/lib/**` ничего не знает о страницах, `src/server/**` не
импортирует компоненты.

### Псевдонимы путей

Заданы одинаково в `tsconfig.json` и `vitest.config.ts`:

- `@/*` → `src/*`
- `@theme/*` → `theme/*`
- `@db/*` → `drizzle/*`

```

├── (app)/
│   ├── cabinet/  сводка, лента заявок обеих ролей, объявления
│   ├── (me)/     мои заявки, профиль, переписка (chat/ — своя раскладка)
│   └── admin/    модерация и справочники (role=admin)
├── (auth)/       вход, сброс пароля
├── api/          auth, oauth/vk, upload, health, search/suggest,
│                 geo/{suggest,reverse,client-index}, dev-ручки
├── layout.tsx    корневой layout: шрифты, темы, шапка, футер, мобильная навигация

├── indexnow.txt/ ключ IndexNow из окружения (route handler)
└── not-found.tsx
```

Личная зона и админка используют общий каркас `AccountShell`
(`src/components/account/`): в кабинете он получает `identity` и рисует
шапку-герой с обложкой, в админке `identity` не передаётся.

Единственное исключение из каркаса — переписка. На десктопе `/chat` это панель
фиксированной высоты со своими скроллами внутри (сайдбар кабинета и заголовок
остаются). На мобиле страница одного треда занимает вьюпорт целиком: заголовок
раздела скрывается, а таб-бар и подвал убираются правилом
`html:has([data-chat-thread])` в `globals.css` — оно же обнуляет `--tabbar-h`,
на которой висят отступ подвала и прилипшие снизу элементы. Скрыть только
компонент таб-бара недостаточно: переменная объявлена на `:root`, и вернувший
`null` компонент её не меняет.

Фиксированная высота — приём **десктопный**. На мобиле её нет намеренно:
`svh`/`dvh` на iOS Safari не реагируют на клавиатуру, и панель заданной высоты
увела бы поле ввода под неё.

## Хедер и то, что уходит под него

Хедер (`src/components/layout/Header.tsx`) — плавающая непрозрачная панель:
сам `<header>` прозрачный и `sticky`, а панель внутри оторвана от краёв,
скруглена и обведена кантом. Стекла в ней нет. Геометрию держат переменные
в `src/app/globals.css`:

| Переменная | Что значит |
|---|---|
| `--header-h` | высота самой панели |
| `--header-inset` | зазор до кромки экрана сверху и до контента снизу |
| `--safe-top` | верхний системный инсет (`env(safe-area-inset-top)`), шапка отступает на него |
| `--header-total` | весь вертикальный след; считается из трёх предыдущих |

`--header-h` и `--header-inset` — голые числа в px: их складывает
`HeaderSearch` через `parseFloat`, а `env()` в JS не разбирается.

**Высоту нельзя менять в одиночку.** Обе обложки профиля уходят под панель до
верхнего края экрана — отрицательным отступом на `--header-total`; фотография
видна в зазорах вокруг неё. От той же величины считаются якорные ссылки
(`scroll-mt`), чтобы заголовок не вставал под панель. Главная под панель не
уходит: её секции — стопка панелей в общем контейнере, и первая из них начинает
контент, а не подкладывается под шапку.
Кто сейчас на неё завязан — покажет:

```bash
grep -rn "header-total" src/
```

Оформление панели (цвета, скругление, отсутствие тени) подчиняется общей
системе — [tokens.schema.md](../theme/tokens.schema.md).

## Нижняя панель на мобиле и safe-area

Таб-бар (`src/components/layout/TabBar.tsx`) — непрозрачная панель во всю
ширину, вплотную к нижней кромке: кант сверху, строка иконок и под ней отступ
на полосу «домой». Его точную высоту держит `--tabbar-h` в `globals.css`.

На карточке чужой вещи нижняя панель другая — полоса брони из
`BookingWidget`, такой же формы. Таб-бар там скрыт правилом
`html:has([data-booking-bar])` в `globals.css`; у владельца полосы нет, и
таб-бар остаётся. Отступ подвала берётся из `--bottom-bar-h` — высоты той
панели, что стоит сейчас. Кнопка полосы не бывает неактивной: пока дат нет или
они заняты, она прокручивает к календарю на странице.

Отступы под чёлку и полосу «домой» работают только потому, что в корневом
`viewport` стоит `viewportFit: "cover"`: без него iOS отдаёт
`env(safe-area-inset-*)` нулями. Боковые инсеты (телефон на боку) получает
`body`; fixed-слои во всю ширину отступают от них сами, их отступы `body` не
трогают. Кто сейчас учитывает инсеты — покажет:

```bash
grep -rn "safe-area-inset" src/
```

Стекло (`.glass`) осталось у выпадающих меню.

## Middleware

`src/middleware.ts` работает на edge и **не обращается к базе**. Делает две вещи:

1. Проверяет **наличие** session-cookie на защищённых префиксах
   (`PROTECTED_PREFIXES` в `src/middleware.ts`) и уводит анонима на
   `/login?from=…`.
2. Прокидывает в RSC флаг `x-has-session` — по нему корневой layout решает,
   поднимать ли сокет доставки, не ходя за сессией в базу.

Это защита от вспышки интерфейса, а не проверка прав: валидность сессии
проверяется дальше, на уровне страницы. Подробности — в [auth.md](auth.md).

Адрес страницы middleware в RSC **не прокидывает**. Приём известный, но
корневому layout'у он не помогает — тот при навигации не перерисовывается;
почему так и что делать вместо — в разделе «Клиентские компоненты».

## Данные

- **ORM:** Drizzle. Схема — `drizzle/schema.ts`, единственный источник правды о
  таблицах. Миграции генерируются из неё (`pnpm db:generate`) и лежат в
  `drizzle/migrations/`.
- **Подключение:** `src/lib/db.ts`, ленивый синглтон `getDb()`.
- **ID:** ULID (`newId()` в `src/lib/id.ts`), лексикографически сортируемый —
  поэтому сортировка по id совпадает с сортировкой по времени создания.
- **Деньги:** целые рубли, `integer`. Дробей и валют нет.
- **Даты занятости:** строки `YYYY-MM-DD`, как их отдаёт Postgres `date`.

Смысл данных и бизнес-правила — в [domain.md](domain.md).

## Геокодер

Адреса ищет свой движок поверх OpenStreetMap и ГАР ФНС, без внешних сервисов
([0021](decisions/0021-own-geocoder-and-listing-coordinates.md)). Геоданные
ключуются **регионом** (`cities.geo_region`), а не городом: город и пригороды
делят один индекс.

| Где | Что делает |
|---|---|
| `src/lib/geocoder/` | движок: нормализация, поиск, обратный геокодер, мини-индекс для браузера. Без БД и сети; устройство — в его `README.md` |
| `scripts/geo-import.ts` | `pnpm geo:import`: JSON `GeoIndexData` → таблицы `geo_*` региона одной транзакцией |
| `src/server/geocoder-index.ts` | таблицы региона → `GeoIndexData`, кэш на `globalThis`, сверка версии по `geo_imports` |
| `src/server/geocoder.ts` | движок региона (лениво, на `globalThis`), подсказки, обратный геокодер, мини-индекс; принимает слаг города |
| `src/server/city.ts` | `getCitiesGeo()` — гео-контекст активных городов (регион, центр, метка данных) без загрузки движка; сбой БД страницам — «геоданных нет», роутам (`strict`) — исключение и 503. `getCityScope()` — набор городов выдачи и точка «Где» для страницы (форма — `src/lib/catalog/city-scope.ts`) |
| `src/app/api/geo/*` | HTTP-роуты поверх `src/server/geocoder.ts` |
| `src/lib/geo/` | без БД: точность точки и её подписи (`precision.ts`), подписи адреса, сверка хитов, хит → колонки адреса объявления и город объявления по адресу (`address.ts`), точка «Где» в адресе страницы (`location.ts`), подпись расстояния (`distance.ts`), гаверсинус |
| `src/server/listing-address.ts` | `resolveListingAddress` — адрес объявления из формы → колонки или отказ; зовут `createListing` и `updateListing` после проверки владельца |
| `scripts/geo-backfill.ts` | `pnpm geo:backfill`: точки объявлениям без них — в `seed_real/listings.csv` (`--csv`) или в базе (`--db`) |
| `src/components/search/AddressCombobox.tsx` | поле адреса: мини-индекс браузера плюс дома с сервера; общее для формы объявления и «Где» |
| `src/components/search/address-client.ts`, `geo-worker.ts` | мини-индекс в браузере: загрузка и сборка в Web Worker, без него — в главном потоке |
| `src/components/search/WhereField.tsx`, `stored-location.ts` | «Где» в панели поиска: адрес или геолокация; последнее место на устройстве |

Страницы движок не загружают: шапке и форме объявления хватает гео-контекста из
`getCitiesGeo()`. Движок строится при первом запросе к `/api/geo/*` или при
первом выборе адреса в форме объявления (сервер сверяет хит в своём движке).

## Мутации: как устроен Server Action

Общая форма — все actions возвращают результат, а не бросают исключение:

```ts
type ActionResult<T = void> =
  | { ok: true; data: T }
  | { ok: false; error: string };
```

Типовой порядок внутри:

1. проверка сессии (`auth()` или `requireAuthState()`), проверка бана;
2. rate-limit (`checkLimit`) там, где действие можно спамить;
3. валидация ввода через zod — payload приходит по сети и типу не соответствует
   автоматически;
4. работа в транзакции, если меняется больше одной таблицы или нужны блокировки;
5. `revalidatePath()` по затронутым экранам.

Проверки прав дублируются на каждом уровне: страница закрыта гардом, но и сам
action самостоятельно проверяет владельца или роль — Server Action доступен по
сети напрямую, минуя UI.

## Кеширование и рендеринг

- Публичные страницы — Server Components с SSR.
- `sitemap.ts` и `robots.ts` помечены `dynamic = "force-dynamic"`: sitemap читает
  БД в рантайме, иначе Next пытается пререндерить его на этапе сборки, где базы нет.
- API-роуты, которым нужны cookies и свежие данные, тоже `force-dynamic`.
- Инвалидация после мутаций — точечная, через `revalidatePath`.

## Клиентские компоненты

По умолчанию всё серверное. `"use client"` стоит там, где нужны состояние,
события или браузерные API: виджет брони, календари, диалоги, формы, переключатель
темы, пикер обложки. Данные в них приходят пропсами из серверных страниц.

**Адрес страницы в шапке читается только на клиенте.** Хедер живёт в корневом
layout'е, а тот при клиентской навигации не перерисовывается: путь и query,
прочитанные там на сервере, протухают на первом же переходе. Серверный вариант
здесь не «менее свежий», а активно неверный — перейдя ссылкой с `/spb` на
`/kazan`, поиск в шапке отправил бы `?city=spb`, то есть заведомо чужой город.

Поэтому текущий город определяют сами клиентские компоненты (панель поиска
`SearchBar`, `CitySelector`, `TabBar`) через хук `src/components/layout/use-current-city.ts`,
а разбор адреса вынесен чистой функцией в `src/lib/catalog/current-city.ts` —
список активных городов приходит пропсом сверху, в БД функция не ходит.

Из адреса город берётся не всегда: на `/`, `/profile`, `/cabinet`, `/u/{id}` и
на `/search` без `?city=` его там нет. Тогда работает **выбранный** город —
`CityPreferenceProvider` в корневом layout'е. Начальное значение считает сервер
(`resolveViewerCity`), дальше его меняет только селектор в шапке, и оно
переживает навигацию, при которой layout не перерисовывается. Провайдер стоит
именно в layout'е, а не внутри шапки: `Header` и `MobileNav` — соседи, и
таб-бару нужен тот же город.

Выбор пишется кукой из server action, а не `document.cookie`: `cookies().set`
заодно сбрасывает клиентский кеш роутера, без чего «Назад» вернул бы страницу
предыдущего города под новым названием в шапке.

### Панель поиска «Что · Когда · Где»

`src/components/search/SearchBar.tsx` — одна форма `role="search"` на
поверхность: в шапке (через `HeaderSearch`) и в hero главной, у каждой свой
`aria-label`. Раскладка под ширину меняется классами, а не второй копией в DOM.

- **Работает без JS.** До гидрации это обычная GET-форма на `/search`: поле
  «Что» названо `q`, город, даты и «Где» из адреса лежат скрытыми полями.
  После гидрации отправку перехватывает `onSubmit` и ведёт по чистой функции
  `searchSubmitHref` (`src/lib/search/submit-href.ts`): подсказка-запрос — на
  её ссылку `/search?q=…&city=…`, раздел — на его канонический путь, текст — на
  `/search`, пустое «Что» — на ту же выдачу с новыми датами и «Где»; даты и
  «Где» панели дописываются всем. Таблица случаев — её тесты.
- **Значения — из адреса страницы.** Шапка не перемонтируется, поэтому поля
  выводятся из `pathname` и query и пересчитываются при их смене, но не под
  руками: поле в фокусе не перетирается.
- **На главной поиск шапки не дублирует hero.** Пока поиск hero
  (`[data-hero-search]`) виден под липкой шапкой, `HeaderSearch` прозрачен,
  держит место в ряду и `inert` — вне касаний, табуляции и дерева доступности;
  ниже `lg` поле «Что» hero отдаёт фокус полю шапки и для этого снимает с него
  `inert`. Видимость — `IntersectionObserver` с верхним отступом в высоту
  шапки; пока внутри фокус (поле, поповер, шторка, панель подсказок), поиск не
  прячется. На любом другом адресе виден сразу; без наблюдателя или без поиска
  hero на странице — тоже. До ответа наблюдателя (сервер, первый кадр) его
  прячет CSS (`visibility`, `globals.css`) и только при поиске hero на
  странице: без JS на главной с поиском hero поиск шапки скрыт целиком, без
  города — виден и работает.
- **Гео-контекст городов** шапка получает от серверного `Header` по всем
  активным городам сразу (`getCitiesGeo`, без загрузки движка): город шапка
  узнаёт на клиенте, а с ним меняется, есть ли «Где» и чей мини-индекс адресов.
- **Списки и календарь — порталом** со слоем `z-50`, выше липкой шапки и
  таб-бара: hero обрезает содержимое, а шапка уже панели подсказок. Ниже `lg`
  «Что» — настоящее поле в шапке, а подсказки — панель на весь экран под ней
  (`MobileSuggestPanel.tsx`) с чипами «Когда» и «Где», которые открывают
  шторку. Активная строка с клавиатуры — `aria-activedescendant` и
  `[role="option"][data-active="true"]` в `globals.css`.
- **Календарь «Когда»** — `react-day-picker` в теме inrenta с выбором в два
  клика в любом порядке (`pickRange` в `src/lib/booking/range-pick.ts`, общий с
  виджетом брони). «Сегодня» панель считает при открытии, а не берёт из
  layout'а: открытая после полуночи вкладка иначе разрешила бы вчерашний день.

Слаги городов — верхний сегмент пути, поэтому `adminCreateCity` не даёт
назвать город как статический маршрут (`RESERVED_SLUGS` в
`src/lib/owner/validation.ts`, там же `search` и `sources`).

## Сборка и деплой

- `output: "standalone"` в `next.config.ts` — Docker-образ несёт минимальный
  рантайм.
- `typedRoutes: true` — ссылки проверяются типами.
- `images.remotePatterns` собирается динамически: фиксированные хосты аватарок
  OAuth плюс хост из `STORAGE_PUBLIC_BASE`. Поэтому переменная нужна **на этапе
  сборки**, а не только в рантайме.
- Миграции применяются автоматически при старте контейнера
  (`scripts/entrypoint.sh`).

Подробности — в [DEPLOY.md](DEPLOY.md).

## Current limitations

Осознанные упрощения текущей архитектуры. Это не список задач — задачи в
[BACKLOG.md](BACKLOG.md).

- **Rate limiter в памяти процесса.** `src/lib/rate-limit.ts` хранит счётчики в
  `Map`, поэтому лимиты обнуляются рестартом и не работают при нескольких
  инстансах. Деплой одноинстансный, это согласованный компромисс.
- **У лимитера два хранилища.** Публичные ручки без входа заводят ключ на
  каждый анонимный IP. В общем хранилище с вытеснением самого давнего ключа
  такой поток выталкивал бы счётчики входа, сброса пароля и суточный лимит
  писем — и молча обнулял бы их. Поэтому виды с `store: "public"` живут в своём
  `Map`, побольше, и при заполнении сначала чистят просроченные ключи. Какие это
  виды:

  ```bash
  grep -n 'store: "public"' src/lib/rate-limit.ts
  ```
- **Индекс поиска — в памяти `app`.** Подсказки «Что» и выдача `/search`
  ранжируются по индексу активных объявлений города, который собирается из БД
  и живёт на `globalThis` процесса `app`
  ([0022](decisions/0022-search-index-in-app-memory.md)). Память растёт вместе с
  каталогом, любая правка объявления сбрасывает индексы всех городов, выдача по
  запросу ограничена потолком совпадений (`RESULTS_LIMIT` в
  `src/server/search.ts`). При нескольких экземплярах `app` каждый держал бы свой
  индекс и догонял чужие правки только сверкой версии.
- **Геокодер — в памяти `app`.** Движок региона со всеми домами живёт на
  `globalThis` процесса `app` и строится при первом запросе адреса, а не при
  старте ([0021](decisions/0021-own-geocoder-and-listing-coordinates.md)):
  первый человек, начавший вводить адрес после рестарта или импорта, ждёт
  сборку, и в этот момент у `app` пик памяти. Новые данные `app` подхватывает
  сверкой версии раз в минуту, но, пока читает их и собирает новый движок,
  держит и старый — поэтому после импорта `app` перезапускают
  ([DEPLOY.md](DEPLOY.md#геоданные-адреса)).
  При нескольких экземплярах `app` у каждого был бы свой движок.
- **Мини-индекс адресов собирается в Web Worker.** Turbopack кладёт модульный
  воркер отдельным чанком со своего домена, и его пропускает `worker-src
  'self'` в CSP — а CSP задаёт только `Caddyfile`: `next start` без Caddy
  политики не имеет, и проверять воркер против неё можно только за Caddy или
  подставив тот же заголовок. Если воркер не поднялся (политика, старый браузер,
  ошибка), индекс собирается в главном потоке в свободное время браузера — на
  слабом телефоне ввод на это время подвисает. Почему так —
  [0021](decisions/0021-own-geocoder-and-listing-coordinates.md#мини-индекс-в-браузере-воркер).
- **Крона нет.** Единственный планировщик в проде — контейнер `backup` (бэкап в
  03:00). Протухание заявок сделано лениво: `expireStaleRequests()` вызывается
  перед чтением списков.
- **Доступ в админку проверяется в layout'е.** `assertAdmin()` стоит в
  `src/app/(app)/admin/layout.tsx`, тогда как комментарий в
  `src/lib/auth/guard.ts` предупреждает, что layout'ы Next кеширует между
  навигациями внутри сегмента. Практического дефекта это не даёт: каждый
  admin-action проверяет роль самостоятельно (`requireAdmin()` в
  `src/server/actions/admin.ts`), то есть данные защищены на уровне мутаций.
  `NEEDS REVIEW`: стоит ли продублировать проверку на самих страницах.
- **Линтера фактически нет.** Конфигурации ESLint в проекте не существует; см.
  [testing.md](testing.md).
